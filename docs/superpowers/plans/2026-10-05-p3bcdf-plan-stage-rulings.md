# P3 子项目 B/C/D/F：计划阶段查出的设计问题与裁决

> 四份实现计划各写完后，作者们都报出了「**在设计里发现的问题**」——**它们没有替设计补写**，
> 这一点是对的（照 P1/P3A 的纪律：计划不替设计做决定）。本文逐条裁决：
> **哪些是设计要改（回到设计作者）**、**哪些接受计划的取法（设计照改）**、**哪些落成遗留（不做）**。
> **本文件生效**；四份计划在 `docs/superpowers/plans/2026-10-05-p3{b,c,d,f}-*.md`。

**通用判据（本次反复用到）**：
- 设计里**成立的绝对措辞**（「堵死」「一律」「都来自」）若只对某个子集成立 → **改措辞 + 写出射程**，不是删。
- 设计里**没有判据**的东西 → **遗留**，不发明。
- **零产生方的类型/变体/迁移** → **删**（不留死物）；与 P1 那次「分支不可达但类型该在」不同——那次保留是因为**该类型确被别处需要**。
- **枚举断言少一只臂**是本项目的既有缺陷类，凡报出即改。

## 五、这些裁决逼出的一条通则

**协调者在派单里把「做成什么样」和「谁来做」混成一句时，两边都会漂。** 本轮 F3 是第三次同形：
我先裁「F 不构造请求类型」（对），又在同一轮顺手写成「F 不命名它」（**过头**——被实现的公开 trait 的签名里必须写出那个类型名）。
**故本条记为派单纪律：凡裁决涉及一个类型，必须分三句写——「谁构造」「谁传值」「谁会在签名里提到它」。**
