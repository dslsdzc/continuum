## 一、四份设计的状态与它们的四处「自足性」差异

四份都**只含设计、不含实现代码**，都过了「交叉复审 → 复核」两轮，再过了**一次整套终审**（`review-set`）。
整套终审的判决按子项目不同：**D 自足**（三张表、状态机、排序接口与基线策略自洽，未决全在规范侧）；
**B/C/F 各卡在别人手里的裁决上**——那些裁决已于 2026-10-05 拍板（见第二节），四份正在折入。

**整套终审独有的价值（逐份评审结构上看不到的东西）**：它查出「约 28 处义务挂在一个**从未具名**的角色
（『执行侧』）上」、`tool` 表的**生产写入方**在一份「指派—退件」闭环里无人认领、以及连接器侧副作用的
`Effect Journal` 产生方未定。**这三条没有一条能由单份评审发现**——这正是 P2b 当年「清理路径绕过 Gate、
审计行从未写下」那一类缺口的同一形状。**结论：并行设计的收口必须有一遍「作为一整套」的评审。**

## 二、四项裁决（2026-10-05）

1. **模型调用路径归新的子项目 G**。它此前是承担约 28 处义务的无名「执行侧」：取 `ProviderHealth`、
   调 D 的 `rank`、发 `ModelProvider::invoke`/`stream`、消费 `RankedExecutionCandidates`、定义 `usage()`
   语义、收紧 `ExecutionProfile`、做模型侧失败分类。**G 与 F 是两条不同路径**（F 是工具调用路径，过强制点 (1)；
   模型调用没有任何强制点）。**G 不得借用 F 的名字**——四份设计混称过，已订正。
2. **§316 的 `invoke` 请求侧要扩一个承载授权/凭据的位置**（**改请求面，不改响应面**——响应在调用完成
   之后才存在，往那里加位置解决不了问题；同 `cancel` 那条裁决的判据）。**这是动 P1 已冻结的接口**：
   `docs/02-工程.md` §10.3 的清单已标注。**C 设计那个位置，F 负责传**；B 不受影响（连接器的凭据交付走
   它自己的「逐次调用的适配器」，不经 §316）。
   **裁决后 C 的 §7.5 把它写死了**（口径唯一，勿再漂）：请求类型装的是**整枚 `&AuthorizedTool`**（＋ `input`），
   **F 只持有并下传它、不读 `granted()`**；**取 `granted()` 的是工具适配器**（`ToolProvider` 的实现），
   在 `invoke` 的实现体内读 `AuthorizedToolInvocation::authorization`、**逐枚取 `Capability::scope()`**
   把这次动作限定在该作用域内（`authorize` 只按 kind 比对，作用域由能力自带）。**选这个形状的判据**：
   没有授权就构造不出这次调用（`continuum-provider` 里的 trybuild 样例），**工具 id 只有一个来源**；
   若让 F 拆出授权值另带工具 id，则「传过去的授权」与「被调用的工具」是**可各自漂移、编译得过**的
   **fail-open 形状**。**注意：这条口径本阶段没有照片**（无真实适配器），是**写死的口径而非可观察事实**。
3. **Connector 归边界层**：`docs/02-工程.md` §4.1 的组件表已把它移出，§5.1/§5.3 已补。
   B 的 `continuum-connector` 因此落**边界层**。B 原先给的第二条理由（层环）**已作废**（箭头方向订正后不构成环）。
4. **§249 的三态是下限**：`stale` 也禁自动路由（§82 的 `ACTIVE → STALE → 重新 profiling`：漂移中的模型
   正在退出服务，放它进自动路由是 fail-open 形状）。

## 四、给实现阶段的四条硬提醒（都是本轮花了代价换来的）

1. **`ALLOWED` 是逐对断言的，且覆盖 dev-dependency**（`every_crate_depends_only_on_its_allowed_set` 跑
   `cargo tree --edges all`）。C 的实现要构造 `Tx` 去调 `authorize`，故 `continuum-provider` 需要
   `continuum-persist` 的 **dev 边**——只加 `Cargo.toml` 不加 `ALLOWED`（或反之）会红。
2. **登记的写点唯一是 `save_tool`**（`continuum-capability/src/persist.rs`）：那条登记期不变量
   （`effect_class` 为 `Some(t)` 时 `required_capabilities` 必含 `for_effect(t)`）**落在它身上**，
   故 F §5.2 那条「工具做了外部效应却没有效应记录」的洞**关在唯一入口上**。
   注意区分两件事：**「谁登记」是 C 的适配器登记入口，「登记项合法吗」是 `save_tool` 的不变量。**
3. **`TaskError` 已决定从 bin 移进 lib**（F 的 N-1 处置）：工具调用路径是**库**函数，而 `TaskError`
   原本定义在 bin（`task_cmd.rs`），故库既调不到它也返回不了它。**移进 lib、变体一个不改、`Cargo.toml` 不动**；
   被否掉的替代是另建一个错误类型（同一批失败两个类型 + 一层逐变体映射）。
4. **否定式照片在本仓是被接受的**：F 的 P-19 是「跑 `task` 路径后断言 `capability grants` 行数为 0」，
   B 的「不写审计」照片是「表行数不变」。**别再把否定命题当作「没有照片」而跳过。**

## 六、流程上值得沿用的两条（本轮的实测）

1. **「四份作为一整套」的评审必须做，而且要在逐份评审之后**：它查出的是「无主义务 / 重复产生点 /
   接缝分歧 / 规范级缺口」这四类——**逐份评审结构上看不到**。
2. **把复审报告落成文件、让作者对着文件修**：本轮四份复审报告都写在 `.superpowers/sdd-p3bcdf/review-*.md`，
   作者按文件逐条处置。**我一次也没有替它们转抄**——转抄正是本项目出错最多之处。
   同理：**协调者也会误派**（本轮我把 F 的两行误发给了 B），而**作者 grep 之后退回、不在自己的文档里
   臆造别人的行**，是正确处置。
3. **折入裁决之后还要走一遍「定点复核」，而它必须由没写过那份设计的人做**：四份设计各自折入四项裁决后，
   本轮派了四个独立代理**只核不改**，判据是「**正文没写＝未落实，消息里说过不算**」。它查出：
   F 有一处**自相矛盾**（§6.5 声明订正了 §11/§14，**漏改 §4.2**，同一份文档里两种说法并存）、
   B 有**一条义务无落点**、D **把已闭记成未闭**、以及**一场 C 与 F 的正面撞车**。
   **这四类没有一类能被作者自检发现**——作者自检用的是自己的口径，而缺陷恰恰是口径本身不一致。
4. **协调者的派单措辞本身就是事实的漂移源**（本轮最贵的一条）。那场 C/F 撞车的**起因是我**：我在派单里
   现编了「F 从 `granted()` 取授权值传过去」，与 C 的设计 §7.5 不符，F 照着做了。**要传的口径必须在设计里
   先写死、再照抄**；**转述一个接缝的两端时，必须把每一端的「同一步骤」写出来**——B 的「取料」是
   「铸出 → `issue`」，我读成了「铸出 → `authorize`」，一字之差，两端被读成不相干的两件事。
   配套的做法：**每条被推翻的说法都把来历留在原地**（`p3a-followups` §一.3 那条因此订正了三回，
   三回来历全留——它本身就是「一处事实的几种记法各自漂移」的标本）。

## 八、子项目 B（`continuum-connector`）实现计划的遗留，逐条落点

本节是 `docs/superpowers/plans/2026-10-05-p3b-connector.md` 末节「遗留」的**权威转录**。
转录的理由：计划的实现过程写在 `.superpowers/`（gitignore 的 scratch），**只留在那里的结论会随 branch 消失**
（同 §七 末段判据）。本子项目已全部落地并提交（收口见该计划 Task 8），本节各条是**未兑现的判据、已声明不是漏接线的留白、
以及本计划自定的取值**，供后继者接手。

凡设计未给判据的，下标「**规范未给判据**」；凡本计划自己定了的，下标「**设计未规定，本计划自定**」。

### 1. `runtime → connector` 本轮无生产消费者（裁决 §七.3，不做 task）

- **机制名**：`continuum-connector` 的入口 `ConnectorRegistry::invoke`（交付于 Task 4/5，全部用例跑在假连接器上）。
- **缺的是哪一步接线**：驱动执行效应今天只有「跑命令」一条路（`Sandbox::spawn`），没有「经连接器执行效应」的路径。
  接上时它是 `main.rs` 装配处的一项（`ConnectorRegistry::new(secrets_runtime)`），并须同步登记 `runtime → connector` 的 `ALLOWED` 条目。
- **后果**：`continuum-connector` 是一个完整实现、自测通过、**但无人调用的 crate**；设计 §10 的第一条完成判据
  在**生产路径上没有落点**（该判据的另一半——编译期与运行期两道关——有照片，见 §10 与本节第 2 条）。
- **这不是漏实现**：设计 §11 第 13b 条已如此声明。
- **收件人：协调者**（派工时决定这条由谁接）。

### 2. `runtime` 装配出的 `SecretsRuntime` 本轮也没有消费者（与第 1 条同源）

- Task 7 按裁决 §七.2 登记了 `runtime → secrets` 并落了 `main.rs` 的装配，但那个运行时的**唯一消费者就是第 1 条里那个不接的入口**。
- 故这条边**按 `cargo tree` 是真依赖、按使用是零消费者**——与「零使用的边即假边」的既有口径**相抵**。
  本计划照裁决落，并在此标出这条相抵供复核。
- **（Task 8 订正：`crates/continuum-runtime/Cargo.toml` 该依赖处的注释原写「这是它的第一个真消费方」，
  与本条相抵、是假话——那条边是**声明在**的而**没有使用**（`main.rs` 的绑定带下划线），该句已作废并改写。）**
- **收件人：协调者。**

### 3. 「一条操作该绑哪一枚 `CapabilityKind`」**规范未给判据**（设计 §3.4、§11 第 16 条）

- 本 crate 保住的只是「不拿到声明的那一枚就走不到实现」，**没保住**「声明的那一枚是对的」。

    **代价说清**：进程环境是共享状态，这条用例会与同 crate 里别的用例争环境，`ENV_LOCK` 必须真的覆盖到。
    **这一条仍开着**（Task 8 订正）：它在**材料期**由环境变量源产出（`source.rs:253` 的 `value_for`，确在入口侧——入口要走 `fetch`），
    差的就是上面那份换源 + 置空进程环境 + `ENV_LOCK` 的夹具，入口实现本身不改。
- **（Task 8 订正原「两条都不是构造不出来」这句）**：如今**只剩 `EmptyMaterial` 一条缺口**——`SourceFormat` 已在启动点闭合
  （见上）。本计划仍不补 task（设计没要求），但**不许含糊过去**：谁在后续补 B 的失败面时，`EmptyMaterial` 是**已知的、可构造的**缺口。
- **收件人：子项目 B 的实现的后续一轮**（或接管连接器失败面的人）。

### 23. **同一个 op 给两条绑定时静默后者胜**（整分支终审查出，**设计/规范的留白**；与 §八.20 同形）

- **位置**：`crates/continuum-connector/src/registry.rs` 的 `ConnectorImpl::bindings` 文档
  （订正前写着「**每个已声明操作恰一条**」）与 `register` 的收尾两行（同文件 `:181-186`）。
- **现象**：`bindings()` 对**同一个 op** 返回两条**不同 kind** 的绑定时，四条核对全过——
  双向覆盖的两次遍历（`any` / `contains`）各命中一次、`DuplicateKindBinding` 因两枚 kind 不同而不撞、
  服务半边也相符；随后 `collect()` 把 `Vec<(op, kind)>` 收进 `HashMap`，**后者胜、返回 `Ok(())`**，
  前一条被悄悄丢掉。入口第 4 步取到哪一条取决于 `Vec` 的顺序。
- **为什么不是实现缺陷**：`register` 做的恰是设计 §3.2.1 写的四条核对；**四条核的是「声明集 ≡ 绑定集的键集」，
  不是「同一个 op 只有一条」**——遍历用的 `any` / `contains` / `HashSet<CapabilityKind>` 都是**存在性**判据，
  没有一条数「同一个 op 出现了几次」。而设计 §6.1 的那十个错误变体里**也没有**对应的一条
  （**没有判据的失败不造变体**——§八.20 同一条纪律）。
- **本计划不补 task、也不发明一条核对**（那会是在规范没给判据处发明一条）。若要定，**两个候选修法**：
  1. **注册期拒**：「同一个 op 至多一条绑定」加进核对 → 需要一枚新的 `Err` 变体（§6.1 的十枚里没有）。
     **代价**：动 §6.1 那张封闭表；且要判「同一 op 重复绑定」是作者笔误还是刻意覆盖——规范未言。
  2. **写明覆盖语义**：在 `ConnectorImpl::bindings` 的文档里写死「同一 op 重复时后者胜」，
     并补一条**顺序敏感**的用例钉住它。**代价**：把一个静默行为升格为契约，调用方从此依赖 `Vec` 顺序，
     而「哪一条在后」跨连接器无从推断。
- **收件人：规范维护者**（§125 的「按操作细分」没有规定「一个操作几条绑定」）；
  另：**B 的实现若要自行定一条**，须标明「设计未规定，本实现自定」并写清代价。
- **与 §八.20 同形**：两条都出在 `register` 末两行对两张 map 的 `insert`，都是**静默覆盖、返回 `Ok`**、
  都在规范/设计里**没有判据**；差别只在覆盖面——§八.20 是**同一个 `ConnectorId`** 整体被替换，
  本条是**同一个 op 的绑定**被替换。两者都使「解析唯一」那条论证多一个前提（§八.20 见下）。
