## 一、四份设计的状态与它们的四处「自足性」差异

四份都**只含设计、不含实现代码**，都过了「交叉复审 → 复核」两轮，再过了**一次整套终审**（`review-set`）。
整套终审的判决按子项目不同：**D 自足**（三张表、状态机、排序接口与基线策略自洽，未决全在规范侧）；
**B/C/F 各卡在别人手里的裁决上**——那些裁决已于 2026-10-05 拍板（见第二节），四份正在折入。

**整套终审独有的价值（逐份评审结构上看不到的东西）**：它查出「约 28 处义务挂在一个**从未具名**的角色
（『执行侧』）上」、`tool` 表的**生产写入方**在一份「指派—退件」闭环里无人认领、以及连接器侧副作用的
`Effect Journal` 产生方未定。**这三条没有一条能由单份评审发现**——这正是 P2b 当年「清理路径绕过 Gate、
审计行从未写下」那一类缺口的同一形状。**结论：并行设计的收口必须有一遍「作为一整套」的评审。**

## 二、四项裁决（2026-10-05）

1. **模型调用路径归新的子项目 G**。它此前是承担约 28 处义务的无名「执行侧」：取 `ProviderHealth`、
   调 D 的 `rank`、发 `ModelProvider::invoke`/`stream`、消费 `RankedExecutionCandidates`、定义 `usage()`
   语义、收紧 `ExecutionProfile`、做模型侧失败分类。**G 与 F 是两条不同路径**（F 是工具调用路径，过强制点 (1)；
   模型调用没有任何强制点）。**G 不得借用 F 的名字**——四份设计混称过，已订正。
2. **§316 的 `invoke` 请求侧要扩一个承载授权/凭据的位置**（**改请求面，不改响应面**——响应在调用完成
   之后才存在，往那里加位置解决不了问题；同 `cancel` 那条裁决的判据）。**这是动 P1 已冻结的接口**：
   `docs/02-工程.md` §10.3 的清单已标注。**C 设计那个位置，F 负责传**；B 不受影响（连接器的凭据交付走
   它自己的「逐次调用的适配器」，不经 §316）。
3. **Connector 归边界层**：`docs/02-工程.md` §4.1 的组件表已把它移出，§5.1/§5.3 已补。
   B 的 `continuum-connector` 因此落**边界层**。B 原先给的第二条理由（层环）**已作废**（箭头方向订正后不构成环）。
4. **§249 的三态是下限**：`stale` 也禁自动路由（§82 的 `ACTIVE → STALE → 重新 profiling`：漂移中的模型
   正在退出服务，放它进自动路由是 fail-open 形状）。

## 三、**仍开着**的规范级缺口（规范没给判据；四份设计均已写明「不发明」）

1. **非效应臂的强制点落在哪里**（§125 的读/草稿类操作，如 `GitHub.read_repo` / `Email.draft`）。
2. **「一条操作该绑哪一枚 `CapabilityKind`」无判据**：`CapabilityKind` 有 12 枚、`for_effect` 的像只有 6 枚，
   作者把 `GitHub.merge` 绑到 `Github(CreatePr)` 或 `Filesystem(Read)` **都会注册成功**（B 的设计已据实如此写，
   并把照片改成**断言 `Ok`**——「正因为没有判据，这条照片才必要」）。
3. **`effect_class` 是否与 `EffectType` 是两个轴**（P3A 设计 §10 第 3 条）：C 曾转给 D，**D 明确退件**
   （它对该字段引用为零，问题两侧都在工具调用路径上，且 D 侧没有可挂的触发条件）。收件人：
   执行侧（工具调用路径）＋规范维护者。
4. **`Trust` 与工具侧 `cost` / `latency` 没有收件人**：P3A 把三者一并交给「子项目 D 的候选排序」，
   而 **D 只接了两个**（复用 `Cost`/`Latency` 落在模型画像上，`trust` 退件——§247 的十二个字段里没有它，
   D 不擅自加规范未给的字段）。**它们同属「工具选择」，而「工具选择」这个组件在 §4.1 里不存在。**
   收件人：后续子项目 / 规范。

## 四、给实现阶段的四条硬提醒（都是本轮花了代价换来的）

1. **`ALLOWED` 是逐对断言的，且覆盖 dev-dependency**（`every_crate_depends_only_on_its_allowed_set` 跑
   `cargo tree --edges all`）。C 的实现要构造 `Tx` 去调 `authorize`，故 `continuum-provider` 需要
   `continuum-persist` 的 **dev 边**——只加 `Cargo.toml` 不加 `ALLOWED`（或反之）会红。
2. **登记的写点唯一是 `save_tool`**（`continuum-capability/src/persist.rs`）：那条登记期不变量
   （`effect_class` 为 `Some(t)` 时 `required_capabilities` 必含 `for_effect(t)`）**落在它身上**，
   故 F §5.2 那条「工具做了外部效应却没有效应记录」的洞**关在唯一入口上**。
   注意区分两件事：**「谁登记」是 C 的适配器登记入口，「登记项合法吗」是 `save_tool` 的不变量。**
3. **`TaskError` 已决定从 bin 移进 lib**（F 的 N-1 处置）：工具调用路径是**库**函数，而 `TaskError`
   原本定义在 bin（`task_cmd.rs`），故库既调不到它也返回不了它。**移进 lib、变体一个不改、`Cargo.toml` 不动**；
   被否掉的替代是另建一个错误类型（同一批失败两个类型 + 一层逐变体映射）。
4. **否定式照片在本仓是被接受的**：F 的 P-19 是「跑 `task` 路径后断言 `capability grants` 行数为 0」，
   B 的「不写审计」照片是「表行数不变」。**别再把否定命题当作「没有照片」而跳过。**

## 五、给子项目 G 的交接

- **它的输入接口由 C 与 D 定**：C 的 `ModelProvider` 调用面（`list_models`/`describe_model`/`health` 取可用性、
   `invoke`/`stream` 发起、`cancel(&stream.call)`），D 的 `RankedExecutionCandidates` 与 `BudgetView`。
- **它要接的义务散在 C 与 D 的「收件人」栏里**（C 约 19 处、D 约 9 处），G 设计时逐条收——**别让它们再悬着**。
- **它是「拿选中的模型去跑」的那一方**，按裁决不得与 F（工具调用路径）混称；两条路径的强制点覆盖不同。

## 六、流程上值得沿用的两条（本轮的实测）

1. **「四份作为一整套」的评审必须做，而且要在逐份评审之后**：它查出的是「无主义务 / 重复产生点 /
   接缝分歧 / 规范级缺口」这四类——**逐份评审结构上看不到**。
2. **把复审报告落成文件、让作者对着文件修**：本轮四份复审报告都写在 `.superpowers/sdd-p3bcdf/review-*.md`，
   作者按文件逐条处置。**我一次也没有替它们转抄**——转抄正是本项目出错最多之处。
   同理：**协调者也会误派**（本轮我把 F 的两行误发给了 B），而**作者 grep 之后退回、不在自己的文档里
   臆造别人的行**，是正确处置。
