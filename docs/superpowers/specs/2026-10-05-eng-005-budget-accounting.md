1. 这条流程引入一个规范点名、而**尚无 crate 对应**的组件：**Budget Validator**。按《工程》§2.1，

2. 「Decision Required」是 §331 的 `Decision { issue, options[], consequences[], blocking }`
   （`docs/spec/05-normative.md:2469`）—— 也在语义层（§2.1 的「Decision 对象与恢复 §331 §332」）。

**颗粒度**：它的**记账机制**要在语义层落地（尚未建），但它的**成本视图**现在就要定——因为
**子项目 D 的 Router 按成本排序候选**（`docs/02-工程.md:266`：「Router 的成本决策依赖该问题的答案」）。

## 三、决定

### 1. 方向：**单一预算树**（原候选 (a)）
节点预算与探索预算都是树上节点的**分配**；§110 的「先找合法低成本方案」由此成为**一次全局判断**。

| 子问题 | 决定 | 依据 |
|---|---|---|
| **扣账顺序** | **预扣—结算**：执行前向父的剩余额度**预留**，执行后按实际**结算** | §110 判的是「**预计**超预算」——没有预留，这一步就没有判据 |
| **嵌套 Intent 的记账** | 子 Intent 的预算 = 父剩余额度的一次分配；**兄弟节点的活跃预留之和 ≤ 父的剩余** | 否则「树」不成其为树，额度会被嵌套凭空放大 |
| **计划期预计超支** | 走 §110：先找合法低成本方案 → 找不到则 `Decision{ blocking: true }`（§331） | §110 原文 |
| **运行期实际超支** | **`FailureClass::Constraint`** ＋ 该节点的 `EscalationPolicy::Decision` | 见下条 |
| **onboarding 开销归属** | **系统级（维护）预算根**，不挂在某个用户 Intent 上 | §22 的 onboarding 可在 Intent 之外发生（`docs/01-总纲.md:1636`）；§12 已把「维护计划」列为后台任务的合法来源之一（`docs/01-总纲.md:1279`） |
| **§334 的「高成本」阈值** | 采纳 §7 的示例数值作为**规范级默认**：`wall_time ≤ 60s`、`money_cost = 0`、`external_side_effect = none`（`docs/01-总纲.md:191`）；策略可在此基础上**收紧** | 闭掉 B3；且它是规范里**已有**的数字，不是新发明的 |

### 2. 「运行期实际超支」为何归 `Constraint`（这一条由用户授权协调者选定）

**判据是已建代码的实际行为，不是语义偏好**（`crates/continuum-graph/src/failure.rs` 的 `decide_retry`，
§309 的固有归属）：

```
CONSTRAINT / AUTHORIZATION            → 直接升级（不重试）
PERMANENT / VERIFICATION / UNKNOWN    → 失败
TRANSIENT / RESOURCE                  → 继续往下判（可重试）
```

- **`Resource` 这条路到不了 §110 的 Decision**：它固有可重试；要走到升级，必须先把 `Resource` 列进
  `retryable_errors` **并且**把尝试次数耗光——那意味着**先无意义地重试几次**。而不列进白名单时，
  它的固有行为是 **`Fail`（不升级）**。两条路都与「进入 Decision」不符。
- **`Constraint` 的固有行为就是升级**，配上节点已有的 `EscalationPolicy::Decision`，**正好落在 §110
  的 Decision Required 上**。语义上也自洽：预算是执行前声明的**约束**，而 §110 那个组件本名就叫
  **Budget Validator**，与 §225 的 **Constraint Validator** 同构。
- **顺带 fail-closed**：`retryable_errors` **只能收窄固有归属、不能放宽**（`decide_retry` 的判定顺序
  第 2 步先于第 3 步），故**即使节点配错，也无法把一次预算违规变成可重试**。
- 「**这一次是预算违规**」这个更细的信息放在**失败的载荷/错误值**里（类别 + 原因），
  不靠新增类别——将来要单独处置时看得到，类别表却不必膨胀。

**因此不新增 `FailureClass` 变体**：P1 的 `FailureClass`、它的 `ALL` 常量与落库编码都不动。

## 四、被否掉的两个方向（连同它们各自的病灶，供后来者不必重走）

| 方向 | 否掉的理由 |
|---|---|
| (b) 三层独立计量、各触发各的 Gate | **§110 要求「先找合法的低成本方案」是一次全局判断**（在三个预算之间选更省的方案），而本方向没有一处能做这个判断——等于把规范点出的病灶（多层各自裁决）原样建出来 |
| (c) 只保留 Intent 级预算，节点级降为估算 | **§246 把 `cost_budget` 列进 `ExecutionProfile`，用意是约束节点执行**；本方向下它不再构成约束，故失去对失控节点的硬边界——§333「Runtime MUST NOT 无限制消耗」在节点这一级将只剩估算，没有强制点 |
