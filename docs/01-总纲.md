# Continuum / PIER 总纲

本文定义 Continuum / PIER 的系统定位、职责边界、核心抽象及各组成部分的设计依据。
本文不规定实施顺序或里程碑安排。已识别缺口见第 9 章，未决事项见第 10 章。

引用编号以 `spec/` 目录为准。

---

# 1. 定位与边界

## 1.1 系统定义

基本抽象不是 `Message → Response`，而是 `Intent → 自主执行`（§1）。

用户提供目标及不可违反的约束；执行过程中的模型选择、Agent 编排、工具调用、资源调度、验证、失败恢复和结果交付由 Runtime 负责。

职责划分如下：

```
用户负责    目标、要求、约束、权限、必要决策
Runtime 负责 拆解、模型选择、推理强度、Agent 创建、工具调用、模态选择、
            执行顺序、并行度、设备选择、资源调度、重试、重规划、
            结果验证、Artifact 管理、后台维护
```

最高抽象（§63b）：

```
Runtime.solve(Intent, Context, Authority) -> Artifact + Evidence
```

其中 Intent 是用户希望达到什么状态，Context 是允许 Runtime 使用的信息和资源，Authority 是 Runtime 在本任务中能产生什么影响。

主要外部接口为 `execute(intent)`，而非 `chat()`。聊天仅作为创建、修改和观察 Intent 的交互方式之一（§63b）。

## 1.2 范围排除

本系统不限定为 Agent Framework，也不等同于 Multi-Agent System、Model Router、AI Assistant 或 Agent OS（§62b）。

现有工作分别覆盖 Agent graph、Agent OS、Model routing、Verifier、Capability security、User preference、Distributed inference 和 Media Agent。本项目不以其中任一方向作为唯一核心，而是将其整合为统一执行链（§62）：

```
Intent → 版本化 Contract → 类型化动态执行图 →
模型/工具/节点/权限路由 → Evidence → 验证 → Artifact → 反馈 → Model Registry
```

核心研究对象不是某一个模型，而是：如何把不可靠、能力各异、成本不同、模态不同的模型，组织成一个长期可靠的执行系统（§62b）。

## 1.3 目标形态

目标形态是持续存在的个人智能计算环境，而非一次请求对应一次回答的会话系统（§1）。

产品层可以将交互简化为单一高层请求，例如“完成该任务”（§148）。

因此，产品目标是使用户只需准确描述目标与约束，由 Runtime 处理其余执行复杂度（§63）。

## 1.4 成功判据

不以支持多少模型、多少 Agent、多少插件衡量（§145）。

核心指标为：**用户仅提供高层目标时，系统在不违反要求的前提下独立完成任务的比例**，以及**完成同类任务所需用户干预次数是否持续下降**。

用户干预次数的下降不得通过越权替用户作出决策实现（§145）。该要求构成系统的首要强制边界。

其他需要评估的量（§61）：任务成功率、Contract 违反率、Verifier 误判通过率、路由后悔度、每完成任务成本、不必要的澄清率、后台有用性、回滚率、Artifact 正确性、权限违反率、恢复成功率、分布式调度效率。

## 1.5 设计原则

系统遵循以下原则：在用户明确的目标、要求与权限边界内，向 Runtime 提供尽可能充分的执行自主性（§146）。

```
high autonomy  ─┐
                ├─ 必须同时存在
hard boundaries ─┘
```

缺少执行自主性时，系统将退化为传统会话式助手；缺少强制边界时，系统将失去可控性。

# 2. 语义：Intent、Specification、Contract、Plan

本层定义任务目标与不可变约束，是用户意图进入系统后的规范化入口，也是所有下游执行约束的来源。

## 2.1 Intent

Intent 是最高层任务对象（§4），不是一次性 prompt，而是支持持久化、暂停、恢复、分解和重新规划的任务实体。

```
Intent {
    id, version
    kind, goal
    status, priority
    created_at, updated_at
    parent_intent?, child_intents[]
    contract_id, active_plan_id?, graph_id?
    product_id?
    completion_predicate
}
```

`kind` 至少支持：TASK、PRODUCT、MAINTENANCE、RESEARCH、BACKGROUND、RUNTIME_IMPROVEMENT（§222）。

状态机（§223）：

```
PROPOSED → SPECIFYING → PLANNING → REVIEW → READY → RUNNING
                                                      ↓
                        WAITING / SUSPENDED / VERIFYING
                                                      ↓
                              COMPLETED / FAILED / CANCELLED
```

Product Intent 在首次达到可发布后可以进入 EVOLVING，而不是直接结束。

**版本化**（§64）：长期任务中用户要求一定会变。Intent 和 Contract 必须有版本。例如，用户提出“该接口不得继续修改”时，应生成 Contract v2，而不是仅向上下文追加非结构化说明。Runtime 必须计算 v1 → v2 的约束差异，然后对已有执行图做：仍然有效的节点保留，结果可能受新约束影响的节点 INVALIDATE，正在运行但违反新约束的节点 CANCEL 或 SUSPEND。

## 2.2 Specification

自然语言 Intent 进入 Planner 前，先编译成 Specification（§227）：

```
Specification {
    goals[]
    invariants[]
    acceptance_predicates[]
    forbidden_states[]
    preferences[]
    unknowns[]          ← 必须正式保存
}
```

`unknowns` 为强制字段。系统 MUST NOT 将未知项自动转换为假设（§227）。在项目层面，第 10 章的未决清单对应这一字段。

## 2.3 Task Contract

任何执行之前，必须先编译成结构化 Contract（§5）。

```
TaskContract {
    id, version, intent_id
    requirements[]      ← 每条带 class 和 verification_requirement
    preferences[]
    prohibitions[]
    budget
    authority_limit
    data_policy, model_policy, node_policy
    acceptance_predicate
}
```

约束分四类（§5、§224）：

| class | 含义 |
|---|---|
| REQUIRED | 必须满足，系统不得自行违反 |
| PREFERRED | 尽量满足，有充分理由时可调整 |
| FLEXIBLE | 明确允许 Runtime 自动调整 |
| UNSPECIFIED | 用户未指定，Runtime 可在 Contract 允许范围内自行决定 |

示例（§5）：用户要"生成一个 10 秒 4K 视频"，得到 `duration = 10s REQUIRED`、`resolution >= 4K REQUIRED`、`codec UNSPECIFIED`、`fps UNSPECIFIED`。

当现有 GPU 无法满足 4K 要求时，系统可以更换模型、节点或 pipeline，也可以采用分块执行或延长处理时间，因为这些调整改变的是 HOW。系统不得将 4K 降低为 1080p，因为这会改变 WHAT；此时必须进入 Decision Required。

**不可越权原则**（§225）：

```
RuntimeFreedom ⊆ ContractAllowedSpace
```

Runtime MAY 换模型、换工具、换节点、换算法、重新规划、改变并行度、改变内部执行顺序。
Runtime MUST NOT 修改 REQUIRED、扩大权限、降低隐私约束、擅自增加高风险外部副作用。

Contract 版本化（§226）：用户改要求时必须创建 vN+1，MUST NOT 原地修改。必须计算 ContractDiff（added / removed / strengthened / weakened），受影响的 ADFIR 节点必须重新判定有效性。

## 2.4 约束门与成本门

执行计划进入运行前过两道独立的门（§6、§7）：

```
候选计划 → 约束验证 → 满足 Contract → 执行
                    → 违反 REQUIRED → 挂起 → 请求用户决定
```

```
探索动作 → 成本门 → 低成本/可逆/短时/无外部副作用 → 自动执行
                  → 高成本 → 请求用户决定
```

默认允许自动执行的探索（§7）：`wall_time <= 60s`、`money_cost = 0`、`external_side_effect = none`、网络传输和算力在阈值内。例如，查询其他节点的 GPU 状态（约 2 秒）或执行 30 秒 probe 可自动进行；下载 40GB 模型、执行 30 分钟替代 pipeline 测试或租用收费 GPU 则需要用户确认。

两类门控必须独立实现：约束门判定操作是否合法，成本门判定操作成本是否可接受。

## 2.5 Plan 与三层审查

```
Plan {
    id, version, intent_id
    type            ← STRATEGIC | EXECUTION
    objectives[], milestones[]
    assumptions[], risks[]
    acceptance_conditions[]
    review_state
}
```

审查状态（§229）：DRAFT → SELF_REVIEWED → AI_REVIEWED → USER_APPROVED；另有 REJECTED、SUPERSEDED。

需要重大用户承诺时，Strategic Plan 必须进入 USER_APPROVED 才能执行。

重大任务的审查阶梯（§207、§338）：

```
草稿 → 自审 → 独立强 AI 审查 → 修订 → 用户审查 → 批准
```

三层职责不同（§208–210、§340）：

- **自审**：查前后依赖、遗漏步骤、重复工作、不可能步骤、Contract 冲突、顺序、验收条件、资源假设。可以自动修正内部不一致。
- **独立 AI 审查**：输入原始 Intent、Contract、Engineering Baseline、草稿计划。重点检查计划是否存在遗漏、是否隐式降低要求、架构是否具备工程可行性、验证是否充分、是否存在可预见的返工，以及是否存在更简化的实现方案。输出 BLOCKER / MAJOR / MINOR / SUGGESTION。
- **用户审查**：审查范围限于战略层，包括目标理解、强制约束、重大架构选择、Milestone、排除项、主要风险、最终完成条件以及成本与权限影响；不要求审查具体函数修改顺序、模型选择、并发度或工具内部步骤。

对应的分工（§211）：

```
用户决定   "我们准备做什么"
Runtime 决定 "如何把它做出来"
```

该职责分离用于避免高自治系统因过度请求用户决策而降低执行效率。

## 2.6 计划变更

执行中可以动态重规划，但要区分两类（§212、§230）：

- **MINOR** —— 换模型、重试、并行调整、工具替换、内部步骤重排。可自动处理。
- **MATERIAL** —— 重大架构变化、Requirement 改变、权限扩大、成本显著扩大、Milestone 目标变化。必须重新触发相应审查门。

计划本身版本化（§213）：Plan v1 已批准后，普通调整是 v1.1、v1.2，可自动；重大变化是 v2，需要重新审查。

约束原则：**Planner 可以优化已批准计划的实现方式，但不得自行修改用户已批准的目标和约束。**

## 2.7 Decision 对象

需要用户决策时，必须创建结构化 Decision 对象，而不应仅发送自然语言问题（§331、§106）：

```
Decision {
    issue
    options[]        ← 每个选项带后果
    consequences[]
    blocking
}
```

规范里给的例子（§106）：

```
当前无法满足 4K。

A. 使用云 GPU    ¥8–12   保持 4K
B. 改成 1080p    免费     违反当前 4K 要求
C. 等待 Desktop 节点上线
```

用户做出选择后（§332、§107）：Decision Result → Contract / Plan 更新 → 图失效 → 恢复执行。

用户选择必须作为结构化 Decision Result 处理，不得将其视为普通会话消息并重新解释整个任务。

触发 Decision 的典型条件（§55）包括：违反 REQUIRED、高成本探索、收费计算、高风险副作用、权限升级和 Trust 变化。Agent 内部的局部执行问题不应默认升级为用户决策。

## 2.8 预算

```
Budget {
    money, wall_time, token, gpu_time, network_transfer
}
```

Runtime MUST NOT 无限制消耗（§333）。寻找替代方案本身也属于预算（§334）。

预计超预算时（§110）：先找合法的低成本方案；找不到时才进入 Decision Required。

# 3. 执行：ADFIR

本层维护统一的通用执行表示，不为代码、视频、3D 和研究任务分别设计独立 Runtime（§8）。

## 3.1 定义

ADFIR —— Adaptive Dynamic Flow Intermediate Representation。

```
ADFIRGraph {
    id, version
    nodes[], edges[]
    entry_nodes[], terminal_nodes[]
    contract_id
}
```

统一表示的元素（§8）：Operator、Artifact、Port、Edge、Activation、Constraint、Effect、Evidence、Verifier。

四个领域最后都落成同一张图：

```
视频    Video → ShotDetect → VisionAnalysis → NarrativePlan → Timeline → Render → Verify
代码    Repository → Analyze → ReproduceBug → Patch → Compile → Test → Verify
3D      Images → CameraPose → Reconstruction → Scene → Render → Verify
```

领域差异通过 Artifact 类型和 Operator 表达，不通过 Runtime 表达（§9、§10）。

## 3.2 Node

```
Node {
    id
    operator
    inputs[], outputs[]
    constraints[], capabilities[]
    execution_policy
    verification_policy
    state
}
```

节点 MUST NOT 直接隐式访问未声明资源（§236）。

状态（§237）：

```
PENDING → READY → QUEUED → RUNNING → VERIFYING → COMPLETED
                                        ↓
                          WAITING / BLOCKED / SUSPENDED
                                        ↓
                          FAILED / CANCELLED / INVALIDATED / LOST
```

## 3.3 Port 与 Edge

每个 Node 的输入输出必须有明确类型（§239）：`Artifact<Image>`、`Artifact<Video>`、`Artifact<Timeline>`、`Artifact<SourceTree>`、`Artifact<Patch>`、`Artifact<TestResult>`、`Artifact<Scene>` 等。

运行时 MUST 拒绝不兼容连接。

Edge 至少支持六类（§238）：DATA（Artifact 流动）、CONTROL（执行依赖）、DEPENDENCY、EVIDENCE（验证关系）、EFFECT、INVALIDATION。

## 3.4 Artifact

```
Artifact {
    id
    type
    content_hash, size
    producer_node, input_artifacts[]
    metadata, provenance
    privacy_class
    version
}
```

三条强制规则：

1. **不可变**（§241）。内容一旦提交 MUST be immutable。修改必须产生 v2，不得覆盖 v1。
2. **可追溯**（§242）。任意最终结果 SHOULD 能反向追溯到原始输入。
3. **隐私分级**（§243）。至少支持 PUBLIC、PERSONAL、PRIVATE、SECRET、LOCAL_ONLY。调度器必须根据 Artifact 隐私等级与节点信任等级判定是否允许将 Artifact 放置到目标节点。

Artifact 是正式执行结果，不是聊天记录的附属品（§9）。复杂任务不能只依赖聊天记录保存状态。

## 3.5 Operator 与后端

```
Operator {
    id, version
    input_schema, output_schema
    determinism
    side_effect_class
    backend_candidates[]
}
```

同一个 Operator 可以有多个后端（§245）：

```
Transcribe
├ local-whisper
├ cloud-model
└ specialized-asr
```

ADFIR 只表达"Transcribe"，具体用哪个后端由 Router 决定。

需要落到具体后端时再做 lowering（§10）：ADFIR → FFmpeg / Blender / Git / GPU backend。

## 3.6 非底层执行原语

Agent 不是一等底层原语（§67）。Agent 是一种执行结构，最终仍然 lower 成 ADFIR 节点：

```
Agent {
    context
    model policy
    capabilities
    subgraph
}
```

因此，single agent、multi agent、subagent、team 和 workflow 均表示不同的图结构，而非独立底层原语。

Agent 生命周期（§68）：CREATED → READY → RUNNING → WAITING → SUSPENDED → VERIFYING → COMPLETED / FAILED / CANCELLED。

长期 Agent 可以 RUNNING → checkpoint → SUSPENDED → 下次 activation → RUNNING。**Agent 不得依赖单一模型的 conversation state 维持可恢复性。**

Agent 之间的上下文默认隔离（§69）。Coding Agent 不得默认获取用户全部会话、其他项目、邮件或 Personal Memory；其上下文应限制为当前任务所需的信息、Contract、相关 Artifact 和必要工具。

原则：**Context 也属于 capability。**

## 3.7 图失效与增量重算

ADFIR 必须支持局部失效传播（§65、§306）：

```
A → B → C → D
         ↓
         E

B 的输入变了：B invalid → C invalid → D invalid
                          E invalid
A 仍然有效
```

允许"改需求、模型失败、Artifact 更新、用户替换输入"之后只重算必要部分。

增量重算（§66、§305）：每个 Operator 应声明 inputs、outputs、dependency hash、side effects、cacheability、determinism。

```
input_hash unchanged  ∧  operator_version unchanged
        ↓
     可以复用已有 Artifact
```

设计目标是 incremental recomputation，而非重新执行整个任务。

## 3.8 调度分三层

三层调度必须相互分离，不得合并为单一且不可拆分的模型决策过程（§301）。

| 层 | 决定什么 | 输入 |
|---|---|---|
| Intent Scheduler | 现在推进哪个 Intent | priority、deadline、blocking、user focus、background suitability |
| Graph Scheduler | 哪些节点 READY、哪些可并发、哪些必须等 | 图结构 |
| Resource Scheduler | 在哪执行、用哪个模型、哪个工具、多少并行 | 资源、成本、隐私 |

Graph Scheduler 主要是确定性 Runtime 逻辑（§303）。

优先级（§300）：

```
用户负载 > 前台 Runtime > 后台 Runtime > 维护
```

公平性（§79）：后台存在多个长期 Intent 时，避免一个大型任务永远占满所有资源。可以支持加权公平调度。

用户显式设置的 priority 拥有最高语义权重（§78）。

## 3.9 失败与恢复

失败分类（§309）：TRANSIENT、PERMANENT、CONSTRAINT、AUTHORIZATION、RESOURCE、VERIFICATION、UNKNOWN。不同类别必须采用不同恢复策略。

```
RetryPolicy {
    max_attempts
    backoff
    retryable_errors[]
    escalation_policy
}
```

**非幂等 Effect MUST NOT 直接自动重试**（§307）。

长任务 Operator 应支持 checkpoint（§308），尤其是视频生成、训练、大规模编译、分布式计算。

节点可能在任务中途消失（§97）。节点应声明 restartable、checkpointable、replicable。临时 GPU 消失时：

```
Running → LOST → 寻找替代节点 → 恢复 checkpoint
```

以避免将局部节点失效扩大为整个 Intent 失败。

高价值任务可以采用投机执行（§98）：在两个节点并行执行相同任务，在首个可靠结果返回后取消另一执行实例。该机制受资源预算限制。

## 3.10 规划方式

Planner 不应一次性生成覆盖完整未来执行过程的大型计划（§75）。默认采用 receding-horizon：

```
当前状态 → 规划最近几步 → 执行 → 获得新信息 → 重新规划
```

该机制用于避免在任务早期基于有限信息过度规划远期执行步骤。

Planner 与 Executor 分离（§76）：

```
Planner   负责 What should happen next?
Executor  负责 How is this node actually executed?
```

Planner 无需感知具体 API、GPU 或 shell command；这些执行细节由 Router 和 Operator 后端处理。

## 3.11 Execution Profile

每次节点执行产生（§246）：

```
ExecutionProfile {
    model?, provider?, tool?, backend?
    compute_node
    reasoning_effort, parallelism
    timeout, retry_policy
    cost_budget
}
```

模型选择不是会话级，而是节点级（§20）。

# 4. 资源：模型、工具、算力、Artifact

本层定义执行资源的选择与承载方式。模型、工具和计算资源均应支持可替换实现。

## 4.1 模型画像

```
ModelProfile {
    id, version
    provider, model_revision
    modalities[], tools[]
    skill_vector
    failure_modes[]
    latency_profile, cost_profile
    evidence_count, confidence
}
```

**不维护单一总评分**（§23、§248）。能力是向量：

```
Reasoning   ├ deduction ├ causal reasoning ├ planning └ constraint reasoning
Coding      ├ understanding ├ bug localization ├ fixing ├ architecture ├ testing └ formal reasoning
Agent       ├ tool use ├ decomposition ├ recovery └ long-task completion
Vision      ├ understanding ├ grounding ├ spatial └ diagram
```

评分不是常数，是时间序列（§24）。每个值包含 score、confidence、sample_count、version、time_range。

评分来源：Standard Benchmark、Active Probe、Population Feedback、Personal Feedback、Verifier Outcomes、Real Task Results。

**必须记录已知失效模式**（§83）。除正向能力评分（例如 `coding = 9.2`）外，还应记录：

```
failure_modes:
  - loses constraints in very long tasks
  - unreliable exact visual counting
  - premature completion claims
  - weak JSON compliance
```

Router 应在任务路由时规避与已知失效模式匹配的候选模型。

**模型身份**不能用 `"model-name"`（§81）。至少包含 provider、model_id、revision、deployment、capability fingerprint。因为同名模型可能被供应商静默更新。

配套的行为指纹（§82）：周期性执行少量稳定 probe；若行为表现发生显著变化，则标记 `profile drift detected`，并将模型从 ACTIVE 转为 STALE 后重新画像，以避免继续使用失效画像。

## 4.2 模型生命周期

```
DISCOVERED → UNPROFILED → RESEARCHED → PROBED → VERIFIED → ACTIVE
异常：STALE / DEGRADED / QUARANTINED / DISABLED
```

Router MUST NOT 自动使用 UNPROFILED、QUARANTINED、DISABLED 的模型（§249）。

新模型不得直接进入自动路由。系统应先创建 Model Onboarding Task（§22）：

```
读官方文档 → 搜 model card → 收集 benchmark → 收集公开 failure mode
→ 生成初步画像 → 执行 Active Probe → Verifier → 生成正式 Profile
```

Profile 记录：modalities、context、tool use、reasoning、coding、vision、audio、spatial、instruction following、constraint adherence、latency、cost、failure modes、known quirks。

## 4.3 模型路由

Router 输入（§250）：TaskSkillRequirement、ModelProfile、CostPolicy、LatencyPolicy、FamilyPreference、FailureHistory。
输出：RankedExecutionCandidates。

选择必须考虑：能力匹配、失败模式、成本、延迟、上下文长度、模态、工具支持、当前可用性。

每次路由除输出 `selected_model` 外，还应输出 confidence、alternatives 和 reason（§84）：

```
Model A   compatibility = 0.91   confidence = 0.94
Model B   compatibility = 0.90   confidence = 0.51
```

在该示例中，A 的能力匹配度与 B 接近，但置信度更高，因此具有更高的路由优先级。

家族偏好（§19）：Auto、OpenAI preferred、Claude preferred、Local preferred、Custom。默认优先同一 family，只有收益明显足够高时才跨 family。Router 考虑 quality、cost、latency、context transfer、family switching、failure risk。

能力档位与推理强度分离（§17、§18）：

```
Tier 1  Free/Light   简单分类、提取、总结、格式转换、机械性代码操作
Tier 2  Normal       复杂推理、代码开发、研究、长上下文、Agent planning
Tier 3  Special      视频生成、3D 生成与重建、专用音频、专用科学模型
```

Tier 3 不代表"更聪明"，代表 specialized capability。

组合方式（§18）：`Tier 1 + low + 大并行` 用于大型机械任务；`Tier 2 + high` 用于复杂核心推理。

自动升级（§85、§251）：

```
Tier 1 → fail → Tier 2 → fail → Tier 2 + high reasoning → fail → cross-family
```

前提是仍然满足 Contract 和 Budget。

自动降级（§86）：复杂规划用 Tier 2 High，随后 400 个机械文件检查降回 Tier 1 Low。这叫 intra-task model scaling。

路由器探索（§27）：Router 不应长期仅选择当前最高评分模型，否则新模型无法积累真实任务反馈。低风险任务可允许小概率探索；高风险任务的探索概率应接近 0。可采用 contextual bandit 类策略。

## 4.4 反馈的三个来源

**Population Feedback**（§25）：大量用户的实际任务结果参与评分。不能简单平均，需要考虑任务难度、模型版本、任务类型、用户是否真实使用、Verifier 能否客观验证、异常评分、刷分行为。

大型项目 patch、完整测试通过、用户接受且长期未回滚等证据，应具有高于简单示例任务和主观星级评价的权重。

**Personal Model Profile**（§26）：冷启动阶段使用 benchmark 与 population 数据；随着个人任务证据积累，其权重逐步提高。最终优化目标是模型在特定用户与任务类型上的实际适配度。

**Runtime Learning**（§216、§320）：记录计划返工模式、模型在不同 Skill 上的失败模式、验证遗漏、Execution Method 的可靠性以及 Context 选择引入的噪声，并据此优化 Planning Policy、Routing Policy、Execution Method、Verification Strategy、Context Selection 和 Scheduling Heuristic。

## 4.5 工具

```
Tool {
    id, version
    input_schema, output_schema
    required_capabilities[]
    effect_class
    deterministic
}
```

Tool MUST NOT 接收未声明 capability（§252）。工具调用应使用结构化输入和受约束的能力声明，Agent 不应通过任意未结构化字符串绕过工具接口约束（§87）。

工具权限通过 capability token 提供（§88、§253）：

```
Capability {
    resource
    action
    scope
    expiry
    issuer
}

例如：
filesystem.read:/project
git.write:/task-worktree
github.create_pr:repo/X
```

禁止 `full_access = true` 作为默认权限。

Git 工具的例子：`git.read`、`git.worktree.write`、`git.commit.local` 与 `git.push` 必须是不同 capability。

**工具调用成功不等价于语义完成**（§89）。`exit code = 0` 不一定说明任务完成。工具结果必须先转成 Evidence，再交给节点的 Completion Predicate 判断。

## 4.6 外部服务

外部服务统一作为 Connector（§124）：GitHub、Email、Calendar、Cloud Storage、CI、Issue Tracker。

Connector 不等于 Agent，它只是 Capability Provider。

权限按操作细分（§125）：

```
GitHub.read_repo / GitHub.create_issue / GitHub.push_branch / GitHub.merge
Email.read / Email.draft / Email.send
```

不得以单一 `GitHub access` 权限覆盖所有操作。

模型接入不绑定某一家（§80、§315）：

```
ModelProvider {
    list_models() describe_model() invoke() stream() cancel() usage() health()
}
```

```
ToolProvider {
    list_tools() describe_tool() invoke() cancel()
}
```

## 4.7 算力

任何满足运行要求的计算设备均可注册为 Runtime 的计算节点（§35）。

```
ComputeNode {
    id
    class          ← PERSONAL | TEMPORARY
    capabilities, resources
    trust, availability
}
```

个人节点（§36）：Phone、Laptop、Desktop、Home Server、NAS。可以有 compute、storage、background task、artifact cache、models、services。

**设备加入网络不等于获得信任**（§36）。

临时节点（§40）：朋友电脑、实验室机器、租用云 GPU、短时服务器。低权限、租约制、计算专用、无长期个人状态、无 Personal Memory、无全局 credential、无网络横向发现。

临时节点执行流程（§40）：

```
ADFIR 子图 → 依赖闭包 → Job Capsule → 临时节点 → 执行 → Artifact → Verifier → 销毁 capsule
```

Job Capsule（§290）仅包含当前任务执行所必需的数据：

```
JobCapsule {
    subgraph
    required_artifacts
    scoped_credentials
    execution_policy
    expiry
}
```

视频生成的例子（§41）：只得到 prompt、reference image、model、generation config；不获得 GitHub token、聊天记录、个人 Memory、其他项目、SSH key。

节点选择考虑（§42、§291）：算力、VRAM、内存、延迟、带宽、成本、隐私策略、信任域、当前负载。

**Artifact 位置也是成本**（§93）。100GB 视频源已经在 Desktop 上时，派给 Desktop GPU 可能比传给 Server 更合理。因此 placement cost = compute cost + data movement cost。

隐私约束可以否决性能（§42）：私人照片标记 LOCAL_ONLY 时，云端节点即使性能最好也不能被选中。

# 5. 边界：工作区、权限、Authority、副作用

这一层定义"什么绝对不能做"，以及违规时靠什么强制。**本层约束必须由 Runtime 强制执行，不得依赖模型自行遵守**（§6）。

## 5.1 默认工作区永久只读

```
BaseWorkspace   = READ ONLY
TaskWorkspace   = 唯一可写位置
```

Runtime 必须保证（§256）：

```
AI_WRITE(BaseWorkspace) = DENY
```

即使模型请求修改 `/home/user/project/file`，Tool Runtime 也必须拒绝，并仅允许写入 TaskWorkspace。该限制必须由文件系统或等价隔离机制强制实现，而不是依赖 prompt 约束（§159）。

Git 项目默认用 git worktree 实现（§255）：

```
project/                     ← 用户工作区
.ai/worktrees/
    intent-102/
    intent-103/
```

每个 Intent 使用独立分支，例如 `ai/task-id`（§16）。Agent 可在该分支中执行修改、commit、reset、测试和重构，但不得修改用户当前 branch。

非 Git 项目可以用 OverlayFS、Btrfs snapshot、ZFS clone、CoW workspace、container layer（§255、§158）。概念不是"Git 分支"，而是更一般的**可写覆盖层**。

## 5.2 合并门

AI 完成的修改要影响用户工作区时，必须经过 Integration Gate（§257、§160）：

```
TaskWorkspace → Integration Gate → BaseWorkspace

支持：查看 Diff / 应用修改 / Cherry-pick / Merge / 丢弃
```

该隔离机制确保实现错误、重构失败、Agent 异常退出或误删除文件时，默认不会影响用户工作区（§160）。

从 AI worktree 向用户 branch 集成修改时，影响域升级为 L3（§16）。

效果等级分层（§15）：

```
L0  只读
L1  计算：build / test / fuzz / benchmark / analysis
L2  可写隔离工作空间
L3  影响用户正式环境
L4  产生外部副作用
```

L2 允许 Runtime 在隔离工作空间内执行写操作；只有跨越隔离边界并影响用户正式环境时才进入 L3。

## 5.3 副作用日志

所有无法通过 Artifact 回滚的外部操作必须进 Effect Journal（§268、§52）：send_email、push_branch、publish、delete_remote、charge、deploy。

```
Effect {
    id, type
    target, parameters
    authorization
    idempotency_key
    state
}
```

执行之前必须记录 intent、authorization、idempotency_key、planned_effect。

状态（§269）：PLANNED → AUTHORIZED → EXECUTING → COMMITTED / FAILED / ROLLED_BACK / UNKNOWN。

Runtime 重启后必须根据 Journal 恢复状态（§269）。目的是避免重试重复产生副作用（§52）。

## 5.4 Authority 与信任域

个人网络 MUST 存在唯一 Authority Host（§292、§38）。它是 Root of Operational Trust，拥有设备加入审批、设备撤销、权限授权、节点身份管理、TOTP secret 管理、trust registry。

普通 Personal Node 不能扩大 Trust Domain。

新设备加入流程（§293、§37）：

```
新设备 → Join Request → Authority Host 上用户明确确认 → 新设备输入 TOTP
→ 绑定设备公钥 → Trusted Personal Node

其他 Personal Node MUST NOT 批准新设备
```

**设备信任与能力分离**（§39）：

```
Trusted Desktop
  ✓ compute
  ✓ background tasks
  ✓ artifact storage
  □ personal memory
  □ mail credential
  □ payment credential

Device Trusted ≠ Unlimited Agent Capability
```

故障转移（§295–297）：

```
PRIMARY_AVAILABLE → PRIMARY_UNREACHABLE → FAILOVER_ELIGIBLE
   → [用户 TOTP 验证] → TEMPORARY_AUTHORITY
```

Temporary Authority 默认不得永久新增 Personal Node、改变根信任、永久撤销核心身份（§296）。它主要用于继续运行现有任务、调度已有节点、访问已有 Artifact。

确认 Primary 永久丢失后，`authority_epoch++`，Standby 晋升为 PRIMARY，旧 Authority 成为 STALE_AUTHORITY（§297、§45）。

**分裂脑防护**（§102）：必须假设 `unreachable ≠ dead`。

Standby 数据加密（§298、§46）：使用随机 256-bit DEK 加 XChaCha20-Poly1305，DEK 用 Standby 设备公钥封装（HPKE / X25519）。

**TOTP 不是加密密钥**（§298、§47）。它只是 Human Failover Authorization。激活条件是：

```
Primary unreachable  ∧  TOTP valid  ∧  Standby Device Key
```

TOTP secret 本身属于高敏感 Authority 数据，应优先存放在 TPM / Secure Enclave / 硬件密钥库，而不是普通配置文件（§100）。

密钥轮换触发条件（§103）：Authority 被攻破、永久 failover、设备撤销、凭据泄露。可轮换 transport keys、session keys、TOTP secret、delegated credentials，但不一定重新生成所有 Node Identity。

## 5.5 密钥

Agent 不直接获得所有密钥（§51）。每个节点只获得 minimum capability、short-lived credential、scoped token。

```
read repository
  ≠
GitHub account full access
```

## 5.6 提示注入

来自网页、邮件、Repository、文档、Issue、工具输出的内容默认属于 UNTRUSTED DATA，不是 instruction（§50）。

Runtime 必须严格区分 Instruction / Data / Capability / Effect 四者，不得仅依赖 LLM 判断输入内容是否构成恶意提示注入（§50）。

上下文里的每一段重要数据都应该知道来源（§281、§71）：

```
source = user_instruction
source = web_untrusted
source = repository
source = verifier
source = memory
source = tool_output
```

外部内容 MUST NOT 与用户指令处于同一信任级别。

原则（§49）：**能使用更低隐私级别的信息完成任务，就禁止请求更高隐私级别信息。**

系统默认仅观察任务状态、项目状态、已授权服务、资源状态以及 Runtime 自身创建的 Intent。
不默认观察：screen、window title、keyboard、browser history、microphone、其他 app 内容。

资源仲裁是这条原则的实例（§13、§300）。默认只读聚合资源状态（CPU、RAM、GPU、VRAM、Disk IO、Network）；明显竞争时才最小化读取高占用进程，且只在本机分类：

```
读取：process name / CPU usage / GPU usage / PID
不读：command line / working directory / window title / screen / open files / keyboard

提供给 AI 的信息仅包括：
  resource_pressure = HIGH
  workload_class = INTERACTIVE
```

以避免将用户行为数据直接传入模型。

## 5.7 策略

用户配置的长期行为规则进 Policy Engine，不是聊天 Memory（§104）：

```
代码任务允许后台自动修复
视频任务超过 30 分钟先问我
禁止使用付费模型
私人照片禁止离开 Personal Network
新模型只允许低风险任务试用
```

优先级（§105）：

```
System Safety
  > Explicit Current Task Contract
  > User Persistent Policy
  > Project Policy
  > Runtime Default
  > Model Suggestion
```

避免不同规则冲突时行为不确定。

## 5.8 审计与持久化

以下操作必须进 Audit Log（§313、§114）：authority 变更、设备加入、设备撤销、capability 授予、外部副作用、Contract 变更、用户批准、Runtime 自更新。

必须持久化的状态（§317、§53）：Intent、Contract、Plan、ADFIR、Artifact metadata、Effect Journal、Authority state、Model Profile、Memory Claim、Policy。

关键状态更新应使用事务（§318）：节点输出提交、Effect 提交、Contract 更新、authority 更新。避免"Artifact 已创建但节点状态仍 RUNNING"这类不一致。

启动恢复流程（§319）：

```
load durable state → reconcile incomplete effects → reconcile running nodes
→ mark lost executions → resume eligible tasks
```

设计目标（§53）是使 Runtime 在异常退出后执行 restart → restore → continue，而不依赖模型回忆此前执行进度。

# 6. 认知：Context、Memory、学习

这一层决定"模型在每一步看到什么"以及"系统跨时间记住什么"。它同时是隐私边界和成本边界的主要执行点。

## 6.1 Context Compiler

不得将全部可用信息无选择地注入模型 context（§70）。节点执行前 MUST 通过 Context Compiler（§279），从 Conversation、Memory、Artifacts、Project、Tool results 里选择最小必要上下文。

```
ContextPackage {
    instructions[]
    references[]
    artifacts[]
    memories[]
    provenance[]
    trust_labels[]
}
```

四个目标（§70）：减少 token、降低隐私暴露、减少无关信息、降低 prompt injection 面。

每个上下文片段都应标注来源（§281）：

```
USER_INSTRUCTION / TRUSTED_RUNTIME / PROJECT_DATA / WEB_UNTRUSTED
TOOL_OUTPUT / MEMORY / MODEL_OUTPUT
```

外部内容 MUST NOT 与用户指令处于同一信任级别。

## 6.2 Memory

Memory 不采用单一全局向量数据库作为唯一抽象（§72）。

**五级作用域**：

| 作用域 | 内容 |
|---|---|
| Session Memory | 当前交互临时状态 |
| Task Memory | 一个 Intent 的长期执行状态 |
| Project Memory | 某个代码库、媒体项目等长期事实 |
| Personal Memory | 用户长期偏好 |
| Runtime Memory | 模型表现、工具行为、调度经验 |

这些数据的权限级别不同。

**来源图**（§282、§170）：长期记忆首先来自 Source，Source 才是事实来源，Memory 是 derived representation。

```
Conversations / Task History / Product History / Project Artifacts
Files / Connected Services / Explicit User Corrections / User Policies
```

**Memory 条目的形态**（§283）：

```
MemoryClaim {
    id, scope
    statement
    sources[]
    validity
    confidence
    last_confirmed
}
```

**基于来源的合成**（§169、§285）。系统不采用逐语句直接写入长期记忆的模式，而是由后台周期运行 Memory Synthesis：

```
近期 Source → 相关历史 Source → 冲突检测 → 时间对齐
→ 重要性估计 → 合成 → Memory Summary
```

触发时机：session 结束后、系统空闲时、大量项目状态改变后、用户主动要求时（§171）。

**Memory 写入范围**（§172）。原始会话本身作为 Source 保留；Memory 仅合成长期稳定偏好、长期项目、重要约束、持续目标、重要关系、常用工作方式和当前长期状态。

```
Source Store    负责保存历史
Memory Synthesis 负责理解历史
```

Memory Summary 是面向用户的可读投影，不等同于底层数据存储（§173）。

**纠正**（§286、§177）：当用户明确指出既有信息已失效时，系统必须定位对应 claim 与 sources，加入 correction source，将旧 claim 标记为 SUPERSEDED，并重新执行合成；不得仅修改 Summary 投影文本。

**forget 与 do_not_mention 必须分开**（§178）。前者作用于 Memory Source / derived memory；后者属于 Interaction Policy。不能把"不希望再提"理解成"历史事实不存在"。

**写入门**（§73）：Agent 不得仅依据自身的重要性判断直接写入长期 Memory。

```
Candidate Memory → classification → scope selection → privacy check
→ deduplication → commit
```

例如，`"该 parser 使用 recursive descent"` 应归入 Project Memory，而非 Personal Memory。

**过期**（§74）：支持 TTL、decay、superseded、invalidated、archived。`Model X 当前价格` 是高时效信息；`Project coding style` 可能长期存在。

**隐私**（§182）：Personal Memory 默认只允许运行于 Authority Host 和 Trusted Personal Node，且需要对应 capability。Temporary Node 默认 `Personal Memory Access = DENY`。确需少量用户上下文时，应通过 Context Compiler 裁剪为 task-specific capsule，而非发送完整 Memory DB。

**与 ADFIR 的关系**（§181）：Memory 不直接变成 prompt。

```
ADFIR Node → Context Requirements → Memory Retrieval
→ Context Compiler → Relevant Memory → Model
```

**用户可见性**（§183）：系统应支持来源可追溯，使用户能够查看某项结论对应的会话、文件或项目记忆来源。

**显式记住**（§176）：用户说"记住这个"时不必创建旧式特殊条目，而是产生 `explicit_by_user = true`、`confidence = high` 的高优先级 Source，参与后续合成。

## 6.3 Runtime 学习与自改边界

Runtime 可学习的对象（§320、§217）：routing policy、planning heuristics、execution method、verification strategy、context selection、scheduling strategy。

Runtime MUST NOT 自动修改（§321）：

```
Authority semantics
Contract semantics
Permission invariants
User approval requirements
Core security policy
```

这些属于 Protected Runtime Core（§322）：

```
ProtectedCore { authority_rules, capability_rules, contract_rules, audit_rules, effect_rules }
```

对它的更新必须显式版本化、独立验证、用户批准。

约束原则（§217）：

> **Runtime 可以学习怎样更好地使用规则，但不能自行取消规则。**

这条同时约束系统自身 —— Runtime 本身也可以成为 Product Drive 的对象（§217），但改进的对象只能是本节列出的可学习对象。

# 7. 长期循环：Product Drive

前述章节定义单个 Intent 的执行闭环。本章定义无固定终点任务的持续推进机制。

## 7.1 两种 Intent

```
普通 Intent    目标明确 → 完成 → 结束
Product Intent 目标是一个最终产品 → 工程化 → 形成里程碑 → 执行 → 验证
               → 继续生成下一里程碑 → 持续推进
```

用户可以只输入（§149）：

> 把这个想法做成一个可以真正发布的软件。

## 7.2 工程可行性优先

Product Drive 的第一阶段应完成工程可行性分析，而不是直接进入实现（§150）：

```
Idea → Requirement Analysis → Engineering Feasibility → Architecture → Engineering Baseline
```

产出：

```
EngineeringBaseline {
    product_goal
    target_users
    required_capabilities
    hard_constraints
    architecture
    technology_choices
    minimum_complete_system
    known_unknowns
    engineering_risks
    acceptance_criteria
}
```

EngineeringBaseline 的目标不是生成 MVP 功能清单，而是明确产品作为完整工程成立所需的架构、能力、约束与验收条件。

例如，对于“AI 视频编辑器”类产品，不应直接将首个 Milestone 定义为 UI 实现；应先明确媒体输入、Timeline、模型系统、渲染、Artifact、项目格式、恢复、导出、权限与资源需求，确保整体架构在工程上闭合。

**本文即为该规则在本项目中的应用结果。** 第 1–8 章展开 Engineering Baseline，第 9–10 章记录 `known_unknowns` 与 `engineering_risks`。

## 7.3 双层循环

Product Drive 不实现为无界 Agent Loop（§185）：

```
外层  Product Loop
      当前产品状态 → 距离成品还缺什么 → 生成下一 Milestone → 重新评估

内层  Milestone Engineering Loop
      Milestone → 规划 → 拆任务 → 实现 → 验证 → 完成
```

内层的执行方式参考 Claude Code / Superpowers 一类工作流（§186）：

```
Milestone → 需求/设计审查 → 实现计划 → 工程任务 → 全新 subagent
→ 实现 → 规格审查 → 质量审查 → 验证 → 下一任务
```

特点是：计划先于实现、任务上下文隔离、逐任务验证、规格审查与质量审查分离。

该方法仅负责“如何完成当前 Milestone”，不负责决定“产品下一阶段的目标是什么”（§186）；后者由外层 Product Loop 负责。

## 7.4 Milestone 惰性生成

这里的“持续”不表示预先生成无限数量的 Milestone，而是指 **Milestone 数量不设固定上限**（§151、§233）。

```
Engineering Baseline → 生成下一批 Milestone → 执行 → 评估产品状态 → 再生成 → ...
```

Runtime 无需预先确定 Milestone 总数；每轮评估应根据当前产品状态与 Product Contract 的差距生成后续 Milestone。

禁止一次生成整个未来无限 Milestone（§233）。

Milestone 之间不一定是线性列表，允许并行与汇合（§152）：

```
        M1
      /    \
    M2      M3
      \    /
       M4
      /    \
    M5      M6
```

因此 Milestone 是高层 Intent Graph（§152）：

```
Product Graph → Milestone Graph → Intent Graph → ADFIR
```

Milestone 状态（§234）：PROPOSED → APPROVED → ACTIVE → VERIFYING → COMPLETED；另有 FAILED、SUPERSEDED。

## 7.5 产品状态评估

每完成一个 Milestone 都要重新评估产品（§153、§232）：

```
ProductReadiness {
    functional, correctness, reliability, performance, security,
    usability, maintainability, deployability, documentation
}
```

应保存 `value + evidence + last_verified`，而不是仅保存主观评分（§232）。

Verifier 不仅检查代码是否可运行，还应判断该 Milestone 是否产生可验证的产品进展（§153）。

## 7.6 无效迭代抑制

持续推进机制不得导致无界计算资源消耗（§154）。

Progress Gate 记录 previous_product_state、current_product_state、progress_delta。连续多个 Milestone 的 `progress_delta ≈ 0` 时，必须停止当前路线、重新分析、更换方案，必要时进入 Decision Required（§337）。

规范给的例子：

```
当前架构已经连续三个里程碑没有解决性能瓶颈。

A. 重构渲染架构
B. 接受当前性能
C. 修改目标硬件要求
```

> **Milestone 数量可以无固定上限，但每次计算必须对应可验证的进展目标。**

## 7.7 可发布状态

Product Contract 必须定义 Shippable Predicate（§335、§155）：

```
核心功能完整 ∧ 没有 blocker bug ∧ 测试通过
∧ 安装流程完成 ∧ 恢复机制完成 ∧ 用户要求全部满足
```

达到后通知用户产品已可发布。

用户启用 Continuous Product Drive 时，可以继续优化、发现问题、增加质量、降低成本、改进 UX（§336）。这些工作属于 post-shippable improvement，**必须与 Shippable 状态区分**，不得因此无限延后“完成”判定（§155）。

## 7.8 后台

软件关闭后，Runtime 可以继续执行授权过的后台任务（§12）。

后台任务来源 MUST 限于：已授权 Intent、policy、维护计划、product drive（§299）。不得仅依据模型自身判断创建无界后台任务。

典型后台任务：Bug scanning、CI verification、static analysis、fuzz、dependency checking、documentation drift、benchmark、project maintenance、artifact preprocessing、media indexing。

```
Repository changed → Background Supervisor → affected modules → spawn scanner
→ 发现 regression → 生成 Intent
```

后台自治针对的是项目与任务世界，而不是持续监测用户行为（§12）。

## 7.9 资源让路

后台任务不能影响用户正常使用机器（§13）。

Resource Arbiter **独立于 AI 模型运行**。默认仅读取聚合资源状态；仅在出现明显资源竞争时最小化读取高占用进程信息；进程名仅在本机用于分类；提供给 AI 的信息限于资源压力与负载类别（详见 §5.6）。

后台任务不应通过直接终止进程作为默认资源让渡方式（§14）。状态机：

```
Running → Throttled → Checkpointing → Suspended → Resume
```

支持 hysteresis —— suspend threshold、resume threshold、cooldown —— 避免资源利用率在临界点反复启停。

## 7.10 会话启动

用户每次打开软件形成一次 Session Activation（§11）。

**Manual 模式**：Runtime 生成候选项（继续 Core / 继续 LCM / 查看昨晚发现的问题 / 开始新对话），用户选择。

**Auto 模式**：启动专门的 Planner Agent：

```
App Open → Session Orchestrator → 分析未完成 Intent → 分析后台新结果
→ 选择当前优先级最高的可继续任务 → 创建 Session Plan
```

例如：

> Core parser 的后台测试结果已生成。当前会话优先继续处理该问题。

随后恢复对应任务。

# 8. 跨领域：代码、研究、媒体、图像

## 8.1 执行方法库

Superpowers 类型的工作流不应成为整个 Runtime 的固定核心（§187）。定义 Execution Method Library，按领域选择可靠做法：

```
software/  planning  TDD  debugging  worktree  review  fuzz  verification
video/     shot-analysis  narrative-plan  timeline-compose  render-review
research/  retrieval  evidence-analysis  contradiction-check  citation-verification
3d/        reconstruction  geometry-validation  render-comparison
```

分工：

```
ADFIR           决定做什么、依赖什么
Execution Method 决定这一类任务怎样做得可靠
```

## 8.2 验证体系

验证体系是系统中风险较高的环节之一，规范定义六层防护机制。

**第一层：测试结果不等价于正确性证明**（§188、§259）。

```
TDD = Implementation Discipline
TDD ≠ Correctness Proof
```

即使满足"先写测试 → 测试失败 → 实现 → 测试通过"，仍然可能存在：需求理解错误、测试断言错误、覆盖范围过窄、Mock 绕过真实路径、遗漏边界条件、测试实现细节而非需求。

> **Tests Passed ≠ Requirement Satisfied**

测试结果在 Runtime 中只是 `Evidence<Test>`，不是 `Proof<Correctness>`（§189）。四个阶段必须区分：

```
Implementation → 产生候选结果
Testing        → 产生证据
Verification   → 判断证据是否充分
Completion     → 判断需求是否满足
```

**第二层：需求覆盖**（§190、§260）。每项 REQUIRED 建立 Requirement → Evidence Set：

```
R1 ├ UnitTest ├ PropertyTest └ FuzzEvidence
R2 ├ IntegrationTest └ IndependentVerifier
R3 └ DifferentialTest
```

即使全部测试通过，只要某项 Requirement 缺少有效证据，状态仍必须为 INCOMPLETE VERIFICATION，不得判定为完成。

**第三层：测试本身要被验证**（§191）。Test Verifier 检查：测试对应哪条 Requirement、断言是否足够强、错误实现是否可能仍通过、Mock 是否绕过真实路径、边界条件是否缺失。

> 测试不能因为存在于 `test/` 目录里就自动被认为有效。

**第四层：变异测试**（§192、§265）。故意把 `x > 10` 变成 `x >= 10`、`x < 10`、`true`、`false`；测试仍通过则证据强度下降。维护 `mutation_score` 作为测试有效性的证据之一。

**第五层：性质与差分验证**（§193）。按任务类型选择 Property-based Testing、Fuzzing、Differential Testing、Metamorphic Testing、Static Verification、Formal Proof。

例子：

```
编译器   Interpreter(program)  ≈  Compiled(program)   可观测行为一致
Parser   parse(serialize(x))   ≈  x
```

此类性质验证相较单个手写用例，更能降低实现对特定测试集过拟合而绕过验证的风险。

**第六层：验证策略本身要被攻击**（§215、§264）。Verifier Adversary 寻找"明显错误但现有 verifier 仍然 PASS"的反例。找到就说明 `verification_strategy = insufficient`，必须增强。

**验证配置按任务分级**（§194、§261）：

```
简单文案修改   → basic verifier
parser 修改    → unit + integration + property + fuzz + mutation
大型重构       → unit + integration + E2E + compatibility + benchmark + differential
安全关键代码   → deterministic vectors + static analysis + independent review + formal verification
```

避免所有任务承担相同验证成本。

**Verifier 优先级**（§262）：

```
1 deterministic checker
2 formal / static checker
3 independent model verifier
4 cross-family verifier
5 human review
```

可确定性验证优先于模型判断。Verifier 必须尽可能与 Worker 隔离（§263）：不应共享完整 Worker reasoning 和 Worker 自己的完成声明；初次验证只输入 Contract、Artifact、Evidence。

**防止 Worker 绕过验证**（§29）：用户要求 4K 时，Verifier 应读取实际 resolution metadata；若结果为 1920×1080，则验证直接失败。Worker 的完成声明不能覆盖该确定性失败结果。

**Worker 与 Verifier 可能共享错误模式**（§120）。因此关键任务应提高验证多样性，例如 different family、different prompt、different evidence path 和 deterministic checker，而不是对同一模型重复执行两次。

**Verifier 分歧**（§121）：A 说 PASS、B 说 FAIL 时不能简单多数投票，应进入 Adjudication —— 运行额外确定性检查、增加第三 verifier、降低结果 confidence、或请求用户决定。

**允许正式表达未知**（§123）：不得要求模型在证据不足时给出确定结论。例如"当前没有足够证据判断该 patch 是否会影响 ARM backend"。之后可以继续验证，或请求用户决定。

**完成条件**（§266、§195）：

```
artifact_exists
∧ all_required_requirements_verified
∧ contract_satisfied
∧ mandatory_effects_completed
∧ no_blocking_verification_failure
```

模型 MUST NOT 自己宣告"我认为已经完成"作为最终依据（§266）。

## 8.3 代码

代码任务的基础是 §5.1 的隔离工作区。L2 默认使用 git worktree，每个 Intent 一个独立分支（§16）。

执行方法的默认形态（§186）：

```
Milestone → 规划 → 拆任务 → 全新 subagent 实现 → 规格审查 → 质量审查 → 验证
```

## 8.4 研究

研究任务拆成固定链条（§330）：

```
Question → Search → SourceSet → EvidenceExtraction
→ ContradictionCheck → Synthesis → CitationVerification
```

## 8.5 媒体

视频领域使用标准 Artifact（§328）：Video、Audio、ShotSet、Transcript、Timeline、SubtitleTrack、Render。不额外创建媒体专属 Runtime。

Timeline 是普通 Artifact（§329）：

```
Timeline {
    tracks[], clips[], transitions[], effects[]
    audio_mix
    metadata
}
```

全自动剪辑的流程（§32）：

```
素材导入 → 镜头切分 → ASR → Audio Analysis → Vision Analysis
→ Narrative Planning → Timeline Artifact → Effects/Subtitle → Render
→ Deterministic Verify → Multimodal Verify
```

素材导入后可在后台进行预处理（§33）：建立 proxy、shot detection、ASR、face/object indexing、visual embedding、beat map、metadata analysis。以降低正式剪辑阶段的等待时间。

这些衍生结果都是 Derived Artifact（§131）：

```
Video ├ Transcript ├ ShotIndex ├ FaceIndex ├ AudioFeatures └ Embeddings
```

原始素材未发生变化时，无需重新计算对应 Derived Artifact。

**生成必须单独授权**（§34）。Task Contract 可以定义：

```
allow_generated_broll
allow_generated_voice
allow_generated_music
allow_frame_interpolation
allow_3d_generation
```

系统不得擅自用生成内容替换原始素材。

## 8.6 图像

区分两种原生操作，不能统一成一个 `image_tool(prompt)`（§161）。

**完整生成**（§323、§162）：

```
GenerateImage { prompt, references[], dimensions, constraints } → Artifact<Image>
```

**局部修改**（§324）：

```
LocalImageEdit {
    source_image
    edit_region
    instruction
    preserve_outside_region = true
}
```

编辑区域支持 Point、Box、Mask、SemanticObject（§325）。

**Point 不是单像素修改**（§164、§325）。用户点击只是交互入口：

```
User Point → Object/Region Detection → Semantic Mask
→ Local Generative Edit → Composite
```

因为生成模型不可能只改一个像素来完成"把手里的手机换成杯子" —— Runtime 要根据点击位置找到 hand + held object 作为编辑区域。坐标统一归一化 `x, y ∈ [0, 1]`（§163），避免与图片实际分辨率绑定。

**局部修改最重要的约束**（§326、§165）：

```
outside_mask_change = FORBIDDEN
```

```
原图 → Region Mask → Generative Inpainting → Generated Patch
→ Hard Composite → Final Image
```

mask 外像素必须直接复制自原图，以防止生成模型对非编辑区域进行隐式重生成。

**谱系**（§327、§167）：每次修改创建新 Artifact，不覆盖原图。

```
Image v1 → edit(face) → v2 → edit(background) → v3 → edit(hand) → v4
```

每步记录 source image、mask、prompt、model、seed、output。用户可以撤销、比较、分叉、继续编辑。

**图像任务的验证**（§168）：检查修改区域是否符合要求、非修改区域是否变化、分辨率是否保持、Alpha/色彩空间是否异常。

`outside-mask pixel difference` 可由确定性检查完成，不依赖模型自述修改范围。

## 8.7 多模态编排

主模型是纯文本时（§31），Runtime 可以自动增加 Image Model、Vision Model、Audio Model、Video Model、3D Model。多模态模型则允许接入 Spatial Tool 一类后端。

**主模型不需要拥有所有能力。** 能力缺口由编排补上，不由模型补上。

# 9. 缺口检查

## 9.1 检查方法

第 5 份材料（§219–348）为规范正文，并使用 MUST / MUST NOT / SHOULD / MAY 表达约束，因此可进行枚举检查。前四份为设计说明，其中自然语言“必须”“不能”等表述不视为规范级强制约束，不纳入本次检查。

检查方法是对以下两类清单进行双向映射：

```
约束清单（§219–348 里所有 MUST / MUST NOT）
      ×
机制清单（规范中声明的全部强制执行机制）
```

分别验证以下关系：

- 每条约束 → 对应的强制执行机制。
- 每个机制 → 对应保证的规范约束。

产出三类问题：

| 类型 | 含义 |
|---|---|
| 有约束无机制 | 规范要求存在，但缺少可执行的强制机制，具体实现可能绕过该约束 |
| 有机制无约束 | 实现机制存在，但缺少对应规范目标，可能导致维护困难或行为边界不明确 |
| 未支撑不变量 | §342 已声明，但缺少足够的下层机制支撑 |

## 9.3 已识别问题

### A 类：有约束，缺少执行机制

**A1. Requirement 覆盖充分性缺少判定标准。**（§195 §260 §261 §266）

约束链是完整的：§260 要求每项 REQUIRED 有 Evidence Set，§266 要求 `all_required_requirements_verified`，§259 禁止把测试通过当成需求满足。

当前规范未定义“充分”的形式化判据。§261 中 `required_evidence_types[]` 由人或模型填写，但缺少机制验证该配置是否与 Requirement 的验证需求匹配。

该项是验证链形成闭环所必需的判定条件，但当前未定义。Completion Predicate 是否成立以及 Intent 是否允许进入 COMPLETED 均依赖该判据。

**A2. 非确定性节点的缓存语义未定义。**（§305 vs §115）

§305 规定当 `input_hash unchanged ∧ operator_version unchanged` 时可以复用已有 Artifact；§115 同时指出模型输出具有非确定性，系统只能提供 execution reproducibility。

因此，若直接按 `input_hash` 复用模型生成的 Artifact，相当于将单次随机采样结果视为输入的稳定函数值。§116 的 Deterministic Mode 是可选开关，默认关。

当前规范未区分确定性节点与非确定性节点的缓存策略，也未定义非确定性缓存的失效条件。

**A3. 三层预算缺少优先级、记账与裁决顺序。**（§246 §333 §334 §110）

节点级 `cost_budget`、Intent 级 `Budget` 与 `Exploration Budget` 同时存在，但规范未定义扣账顺序、嵌套 Intent 的记账方式以及超预算时的裁决优先级。

另一个缺口是：§22 的 Model Onboarding 需要执行 probe，而 §7 中下载 40GB 模型属于高成本动作；但 onboarding 可能发生在具体 Intent 之外，因此缺少明确的 Intent 预算归属。规范尚未定义该类开销的记账位置。

**A4. Population Feedback 的数据来源与治理机制未定义。**（§25 §26）

§25 要求"大量用户实际任务结果"参与模型评分。这是个人 Runtime。

规范未定义 Population Feedback 的聚合主体、去标识化方式、冷启动数据来源，以及外部反馈不可用时 Router 的降级策略。§26 定义了 Personal Profile 作为长期方向，但 §25 与 §26 之间的权重切换条件尚未规定。

**A5. Verifier 独立性不可用时缺少降级路径。**（§262 §263 §126）

§262 的优先级第 3 项为“独立模型 Verifier”，第 4 项为“跨 family Verifier”。在单用户、单一 provider 或 §126 所述离线模式下，这两类资源可能不可用。

规范未定义上述资源不可用时的降级路径，例如回退到确定性检查、提高 confidence 门槛，或显式降低 verification level。

**A6. VerificationProfile 生成过程缺少独立验证。**（§194 §261 §215）

§194 说"不同任务自动生成 VerificationProfile"。生成者只能是模型。

§215 的 Verifier Adversary 仅覆盖 Verifier 本身，未覆盖 VerificationProfile 的生成阶段。§191 的 Test Verifier 负责检查具体测试，而 VerificationProfile 位于其上游并决定所需验证类型。

**A7. Artifact 隐私等级的赋值与传播规则未定义。**（§240 §243）

该字段已定义，且调度器 MUST 使用，但规范未规定默认值、设置权限以及派生 Artifact 的继承规则。

具体未决项包括：PRIVATE 输入派生 Artifact 的默认等级、不同隐私等级 Artifact 合并时的传播规则，以及模型生成内容的初始隐私等级。

**A8. 两套身份系统，关系未定义。**（§221 §240）

§221 要求所有持久对象有稳定 ID（`artifact://...`），§240 的 Artifact 又有 `content_hash`。

两者之间的主从关系、失效判定依据及变更触发规则尚未定义；§242 的 lineage 追溯使用何种标识也未规定。

**A9. 设备侧 capability 分类法不存在。**（§39）

"Device Trusted ≠ Unlimited Agent Capability" 是明确的原则，例子列了 compute、background tasks、artifact storage、personal memory、mail credential、payment credential。

上述内容仅构成示例，尚未形成完整分类法。规范未定义 capability 枚举、默认授予集合，以及设备能力判定机制。

**A10. "Primary 永久丢失"无法确认。**（§297 §102）

§102 明确要求假设 `unreachable ≠ dead`。§297 却要求"确认 Primary 永久丢失后"才能 promotion。

规范定义了状态机，但未提供“永久丢失”的判定条件。这属于分布式一致性与故障判定问题：在缺少第三方仲裁的个人网络中，需要区分“暂时不可达”与“永久丢失”。当前架构实际依赖人工确认，但规范尚未将其明确为人工决策。

**A11. 跨节点一致性模型未定义。**（§318 §297）

§318 规定关键状态更新应使用事务，但 Authority 与各 Personal Node 之间采用线性一致、因果一致还是最终一致，当前尚未定义。

相关未决项包括：epoch 变更（§297）时未提交事务的处理规则，以及 §294 中 signed registry replica 的同步周期与允许滞后阈值。

**A12. Event Stream 的 schema 与版本规则未定义。**（§310 §135）

规范列出了十一个事件名称（如 `intent.created`、`node.started`、`artifact.created`、`decision.required`、`verification.failed`、`task.completed`），但未定义字段结构与版本兼容规则。

根据 §135，前端以 Event Stream 作为消费接口，因此事件结构属于对外契约，应定义版本化与兼容策略。

**A13. 边界执行机制自身归属未定。**（§320 §321 §322）

§320 允许学习 routing policy、planning heuristics、execution method、verification strategy、context selection；§321 禁止自动修改 Authority、Contract、Permission、approval、security 语义。

但规范未定义**执行该分界线的机制**自身属于哪一类。如果该机制也可被学习或修改，则会形成自引用风险，例如 Runtime 可能重新分类受保护项。

**A14. Resource Arbiter 的最小暴露面缺少强制机制。**（§300 §13）

§300 说 SHOULD 只向 AI 暴露最小化资源结论。SHOULD 意味着可以偏离。§13 描述了设计意图（只传 `pressure` 和 `workload_class`），但它不是规范段。

当前缺少强制机制，无法保证实现不会将进程名、路径等超出最小暴露面的信息传入 Context。

**A15. Progress Gate 的 `progress_delta` 缺少度量定义。**（§337 §232 §153）

§232 用九个维度描述 ProductReadiness，§153 要求每个 Milestone 后重新评估，§337 要求 `progress_delta` 接近零时触发重新规划。

但规范未定义九个维度的聚合函数及 `progress_delta` 阈值，因此当前实现无法确定 Progress Gate 是否应触发。

### B 类：有机制，缺少对应约束

**B1. Verifier Adversary 为 MAY。**（§264）规范未规定其强制触发条件；“高价值任务”尚未定义，相关成本归属也未明确。

**B2. Checkpoint 为 SHOULD。**（§308）规范未定义必须支持 checkpoint 的 Operator 类型，也未定义 checkpoint 写入失败后的恢复策略。

**B3. Exploration Budget 在规范段缺少阈值。**（§334）规范仅要求“高成本探索必须进入 Decision Gate”，具体阈值仅在 §7 的设计示例中出现，因此缺少可执行的规范级默认值。
**已闭（2026-10-05）**：把 §7 的示例数值提升为规范级默认（`wall_time ≤ 60s`、`money_cost = 0`、`external_side_effect = none`），策略可在其上收紧。依据见 `docs/superpowers/specs/2026-10-05-eng-005-budget-accounting.md` 第三节第 1 条。

**B4. Audit Log 缺少防篡改机制。**（§313）规范列出了必须记录的事件类型，但未定义保留期与篡改检测机制。§114 中“不可轻易篡改”仅属于设计说明，不构成规范级约束。

**B5. Temporary Authority 的限制用 SHOULD。**（§296）这是 trust 边界，"默认 SHOULD 禁止"意味着有理由即可偏离。建议提升为 MUST 并列明例外，否则 §342 第 7、8 条不变量在下游是软的。

### C 类：规范内部冲突或边界不明确

**C1. §249 对 UNPROFILED 模型的使用限制与 §27 的路由探索存在边界冲突。** Onboarding probe 需要在任务分布上执行，但规范未定义 probe 是否属于 §249 所称的“使用”，也未定义该阶段的例外范围。

**C2. §233 的"下一批"边界未定义。** 有限视野规划会生成下一批 Milestone，但 §152 允许 Milestone Graph 并行与汇合，因此“下一批”可能覆盖多个未来状态。

**C3. Verifier 独立性与强度冲突时无裁决顺序。**（§263 vs §340）§263 要求与 Worker 隔离，§340 要求独立审查优先用更强模型。只有一家强模型时两者不可兼得。

**C4. Context Compiler 是否属于安全边界。**（§279 vs §69）§279 要求节点执行前 MUST 通过 Context Compiler，§69 说 Context 也属于 capability。因此需要明确 capability 判定发生在 Compiler 内部还是外部；该选择决定 Compiler 是否必须纳入 §322 的 Protected Core。

### D 类：§342 的十条不变量本身

逐项映射后，第 5、9、10 条不变量仍缺少充分的机制支撑：

## 10.5 需要用户决定的项

以下事项属于设计取舍，而非直接的技术缺口；现有规范保留了多个可行选项：

**D-1. 边界层采用 L0–L4 影响域分级（§15），或采用 capability token 逐项授权（§253）。** 两者均已出现在规范中；前者提供粗粒度影响域分类，后者提供细粒度授权，但二者的映射与切换关系尚未定义。

**D-2. Memory Summary 是否允许用户直接编辑。** §173 将其定义为 human-readable projection，§183 要求来源可见；但规范尚未定义用户修改投影后如何映射回 Source。

**D-3. Agent 的粒度与数量上限。** §67 将 Agent 定义为图结构，§69 要求上下文隔离，但规范尚未规定单个 Intent 可派生的 Agent 数量上限及相关成本归属。

# 结语

第 1–8 章是这套系统的完整形态，第 9 章是它的缺口，第 10 章是这些缺口的处理状态。

以下三项构成系统的核心不变量，其余机制均依赖这些约束：

1. **Contract 不可越权**（§225）—— Runtime 可以改变 HOW，不能改变 WHAT。
2. **Base Workspace 不可写**（§256）—— AI 的错误默认不落到用户真实工作区。
3. **完成不由模型宣告**（§266）—— 由 Completion Predicate 与 Evidence 裁定。

第 9 章识别的 A1、A2、A3、A5、A6、A8、A12 均直接影响上述核心不变量的可执行性，因此应视为前置设计问题，而非实现细节。

产品层最终可将用户交互收敛为一个高层目标：**完成该任务。**

其余执行复杂度由 Runtime 承担。
