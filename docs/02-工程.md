# Continuum / PIER 工程文档

本文定义 Continuum / PIER 的建设内容、组件边界、依赖关系与完成判据。
本文不规定实施顺序或里程碑安排。层级编号与《总纲》第 1–8 章对应。

---

# 1. 技术栈与绑定范围

## 1.1 绑定原则

§346 要求 PIER 模型无关、Provider 无关、工具无关、计算节点无关、前端无关。该约束的对象是核心语义，不涉及实现语言。

本文采用分层绑定：

| 范围 | 是否绑定 | 内容 |
|---|---|---|
| 核心 | 绑定 | ADFIR 执行内核、持久化、调度、Capability 强制、Verifier 判定 |
| 外围 | 中立 | 前端、Connector、模型适配器、插件、算子后端 |

划分依据是对外接口的存在性：外围部分在规范中已有明确的接口定义（§315 ModelProvider、§316 ToolProvider、§124 Connector），核心部分没有，且核心的不变量需要结构性保证。

## 1.2 核心语言

核心采用 Rust。选择依据是 §239、§236、§253 三条约束都要求运行时强制，而不是编译期约定：

```
§239  运行时 MUST 拒绝不兼容连接
§236  节点 MUST NOT 直接隐式访问未声明资源
§253  禁止 full_access = true 作为默认权限
```

类型在运行时被擦除的语言需要为这三条各建一层手工校验。手工校验层是 §342 十条不变量最容易失效的位置。Rust 的代数数据类型与新类型模式可以把其中一部分变成结构性约束：不兼容的 Port 连接在类型上不可构造，Capability 与裸字符串在类型上不可互换。

其余两条依据：

```
§305 §318 §319   增量重算、事务边界、崩溃恢复要求持久化具备事务语义
§10  §245        算子最终 lower 到 FFmpeg / Blender / Git / GPU backend，
                 核心不承担媒体与模型生态
```

第二条排除了以生态为由选择核心语言的推理。

## 1.3 实现方式

从零实现，不基于现成 agent 框架。Claude Code、Superpowers 等仅作设计参考素材（§186 已将其定义为 Execution Method 的一种来源，而非 Runtime 的固定核心）。

## 1.4 组件方向

以下为方向性选择，不作为规范级约束。标注「载荷」的项改动成本高，标注「可替换」的项在接口边界内可换。

| 用途 | 方向 | 性质 |
|---|---|---|
| 异步运行时 | tokio | 可替换 |
| 序列化与 schema | serde | 载荷 |
| 持久化 | SQLite（需事务，§318） | 载荷 |
| 内容哈希 | 密码学哈希（§240 content_hash） | 可替换 |
| 快照加密 | XChaCha20-Poly1305 + X25519 封装（§298） | 载荷 |
| 算子与插件隔离 | 子进程 + 受控 IPC（§91 插件沙箱） | 载荷 |
| 前端 | 中立 | — |
| 模型与工具适配器 | 中立，经 §315 / §316 接口 | — |

## 1.5 外围中立边界的实现要求

外围中立不等于无约束。中立部分的每次调用都必须经过核心的 Capability 判定（§253）。中立边界的实现要求是：外围组件不能持有核心状态，只能通过接口请求。

# 2. 语义层工程

对应《总纲》第 2 章。本层不依赖任何下层，是纯语义处理。

## 2.1 建设内容

| 组件 | 规范依据 |
|---|---|
| Input Canonicalization Frontend | §270 §196 §197 |
| Reference Resolver | §271 §272 §273 §274 §275 §276 §277 §278 |
| Intent 存储与状态机 | §222 §223 |
| Specification 编译 | §227 §214 |
| Contract 编译与版本化 | §224 §226 |
| ContractDiff 计算 | §226 |
| Plan 与审查状态机 | §228 §229 §338 §339 §340 §341 |
| Plan Change 分类 | §230 |
| Decision 对象与恢复 | §331 §332 |
| Constraint Validator | §225 §6 |
| Budget 与探索预算 | §333 §334 |
| Budget Validator（预算超支的裁决路径） | §110 §333 §334 |

## 2.2 组件边界

**Input Canonicalization Frontend** 是 Intent 进入系统的第一道处理，位于 Intent Compiler 之前（§270）。组件包括 Surface Normalizer、Mention Detector、Candidate Retriever、Reference Resolver、Alias Resolver、Temporal Resolver、Ambiguity Manager。

**Reference Resolver** 输出四态之一：`Resolved / ConfirmRequired / Ambiguous / Unknown`（§271）。核心语义基于候选集合与显式约束，不基于评分公式（§201）。候选检索分数仅用于排序，不得当作真实概率（§272）。

Resolver 必须保留 UNKNOWN 与 NIL 的可能（§273），不得因 Registry 中存在候选就强行绑定。解析强度门槛随后续动作风险提高（§276），语义确定与允许产生副作用是两个独立判定。

Alias 分四级作用域，Session Alias 不得默认永久化（§278）。

**Specification 编译** 输入自然语言 Intent，输出 `goals / invariants / acceptance_predicates / forbidden_states / preferences / unknowns` 六元组。`unknowns` 是强制字段（§227），不可为空时也必须显式保存。

**Contract 编译** 输入 Specification，输出带版本的 `TaskContract`。每条 Requirement 带 `class` 与 `verification_requirement` 两个字段（§224）。

**ContractDiff** 输入两个 Contract 版本，输出 `added / removed / strengthened / weakened` 四类差异。输出被第 3 层的图失效传播消费（§226）。

**Constraint Validator** 输入候选计划与当前 Contract，输出通过或违反。违反 REQUIRED 时进入挂起并创建 Decision（§6）。本组件是 §342 第 1 条不变量的执行点。

**Constraint Validator 与 Budget Validator 必须分离**（§6 §7）。前者判定合法性，后者判定成本可接受性。

## 2.3 层内依赖

```
Input Canonicalization ← 无
Reference Resolver ← Input Canonicalization + Alias 存储 + Registry
Specification 编译 ← Intent 存储（经 Canonicalization）
Contract 编译 ← Specification
ContractDiff ← Contract 版本存储
Constraint Validator ← Contract + Plan
Plan 审查 ← Plan + Contract + Specification
```

无循环。

## 2.4 完成判据

给定一句自然语言 Intent，能够产出：

```
含错别字、简称、中英混写、代词的输入被规范化，或被明确标记为 Unknown / Ambiguous
不存在正确候选时系统不强行绑定（§273）
带版本的 Specification，且 unknowns 显式保留
带版本的 Contract，每条 Requirement 带 class 与 verification_requirement
ContractDiff 能正确判定哪些已有节点受影响
违反 REQUIRED 的候选计划被拦截并生成 Decision
```

## 2.5 相关缺口

`verification_requirement` 字段（§224）的取值依赖 OPEN-001。该字段可以存储，但在 OPEN-001 解决前无法判定其是否被满足。这不阻断本层建设，阻断的是第 8 层的验证收口。

# 3. 执行层工程

对应《总纲》第 3 章。本层是系统规模最大的一层，也是 Rust 选择收益最直接的一层。

## 3.1 建设内容

| 组件 | 规范依据 |
|---|---|
| ADFIR 图数据结构 | §235 |
| Node 与状态机 | §236 §237 |
| Edge 六类型 | §238 |
| Port 类型系统与运行时校验 | §239 |
| Artifact 数据模型 | §240 §241 §242 §243 |
| Operator 注册表与后端解析 | §244 §245 |
| Planner 接口（receding-horizon） | §75 §214 |
| ExecutionProfile | §246 |
| Graph Scheduler | §303 |
| 图失效传播 | §306 |
| 增量重算与 Artifact 复用 | §305 |
| 失败分类、重试、检查点 | §307 §308 §309 |

## 3.2 组件边界

**Port 类型系统** 是本层唯一必须由类型系统承担的部分。§239 要求运行时拒绝不兼容连接，实现方式是把 Artifact 类型编码为封闭的代数数据类型，连接构造时校验。

**Artifact Store** 实现两条硬约束：内容不可变（§241，修改产生新版本而非覆盖）、lineage 可追溯（§242，任意结果可反向追溯到原始输入）。

Artifact 的两个标识（`id` 与 `content_hash`）的主从关系依赖 OPEN-005，在本项解决前不能确定图失效以哪个为准。

**Graph Scheduler** 主要是确定性逻辑（§303），不涉及模型决策。职责是判定哪些节点 READY、哪些可并发。

**图失效传播** 沿 DEPENDENCY 与 INVALIDATION 两类边传播。不相关节点不得重算（§306）。

**增量重算** 的复用条件为 `input_hash unchanged ∧ operator_version unchanged ∧ contract unaffected`（§305）。该组件与 OPEN-002 直接冲突，见 3.5。

## 3.3 层内依赖

```
Port 类型系统 ← 无
Operator 注册表 ← Port 类型系统
Node 状态机 ← Operator 注册表
ADFIR 图 ← Node + Edge
图失效传播 ← ADFIR 图
增量重算 ← 图失效传播 + Artifact Store
Graph Scheduler ← ADFIR 图
ExecutionProfile ← Node
```

## 3.4 完成判据

```
一张 ADFIR 图能完整执行，节点状态严格按 §237 迁移
输入 Port 与输出 Port 不兼容时，连接在构造阶段即被拒绝
修改一个节点的输入后，只有其下游被 INVALIDATED，上游与无关分支不动
失败按 §309 分类，非幂等 Effect 不进入自动重试（§307）
```

## 3.5 相关缺口

**OPEN-002 直接阻断本层的增量重算组件。** §305 的复用前提是 `input_hash unchanged`，§115 承认模型输出非确定。由模型产出的 Artifact 按输入哈希复用，等价于把单次采样当作输入的稳定函数值。在 OPEN-002 解决前，增量重算只能对确定性节点实现，非确定性节点的行为未定义。

**OPEN-005 阻断 Artifact 身份判定。**

# 4. 资源层工程

对应《总纲》第 4 章。本层确定执行资源的选择与承载方式，模型、工具、计算资源均支持可替换实现。

## 4.1 建设内容

| 组件 | 规范依据 |
|---|---|
| ModelProfile 与 SkillVector 存储 | §247 §248 |
| Model Registry 生命周期 | §249 |
| Router 与候选排序 | §250 §84 |
| 升级与降级 | §251 §85 §86 |
| 路由探索 | §27 |
| Provider Adapter（中立） | §315 §80 |
| Tool Registry 与 Capability Token | §252 §253 §87 §88 |
| ToolProvider（中立） | §316 |
| Compute Node 注册 | §287 §288 §289 §290 §291 |
| 节点放置 | §291 §243 §93 |

## 4.2 组件边界

**Capability Token** 是本层最需要结构性保证的部分。§253 禁止 `full_access = true` 作为默认权限，因此 Capability 必须是显式构造的、带 resource / action / scope / expiry / issuer 五要素的类型，而不是布尔量或字符串。

Capability 的三个强制点分布在三层：本层的 Tool Registry（工具调用前）、第 5 层的执行点（实际副作用前）、第 5 层的密钥运行时（凭据签发）。

**Router** 输出排序后的候选而非单一选择（§250），并附 confidence、alternatives、reason（§84）。选择依据不含 `overall_score`（§248 明确禁止）。**它的成本输入是「预算视图」**（剩余额度，而非一个总数）——依据 OPEN-003 的裁决（`docs/superpowers/specs/2026-10-05-eng-005-budget-accounting.md`）。**该视图由哪一层提供**（语义层的 Budget 属第 2 层，故这可能是一条跨层边，受 §9 管辖）在冻结本层接口时一并定，本处只固定「Router 收的是视图」这一形状。

**Model Registry 生命周期** 决定哪些模型可被自动路由。§249 规定 Router 不得自动使用 UNPROFILED、QUARANTINED、DISABLED 三类状态。

**Provider Adapter** 与 **ToolProvider** 是中立边界，核心不能持有其实现细节，只能通过 §315 / §316 定义的接口调用。

**节点放置** 必须同时满足隐私约束与性能目标，隐私优先（§42）。放置成本包含算力成本与数据搬运成本（§93）。

## 4.3 层内依赖

```
SkillVector ← 无
ModelProfile ← SkillVector
Model Registry ← ModelProfile
Router ← Model Registry + continuum-capability 的两个类型（`Cost` / `Latency`）      订正于 2026-10-05：本层对那个 crate 的依赖是**取这两个类型**（落在模型画像的 cost/latency 上），不是能力凭据；原写「Capability Token」在组件层名不符实（D 的设计 §8.4 指出）
Provider Adapter → 被模型调用路径（子项目 G）调用，接口中立      订正于 2026-10-05：Router 只出排序、不调用适配器；调用方按角色命名，2026-10-05 起该角色具名为子项目 G
ToolProvider → 被工具调用路径调用，接口中立                    补于 2026-10-05：本层的第二个中立边界（§316）
Tool Registry ← Capability Token
Compute Node 注册 ← 无
节点放置 ← Compute Node 注册 + Artifact 隐私等级 + Router 输出
```

## 4.4 完成判据

```
给定任务能力需求，Router 输出带 confidence 的候选排序，且不依赖单一总分
未完成画像的模型不会进入自动路由
工具调用前校验 Capability，且 Capability 不可与裸字符串互换
隐私等级为 LOCAL_ONLY 的 Artifact 不会被放置到云端节点
```

## 4.5 相关缺口

**OPEN-003 已决（2026-10-05），不再阻断预算组件。** 节点级 `cost_budget`（§246）、Intent 级 Budget（§333）、Exploration Budget（§334）三层取**单一预算树**（节点预算为父预算的子分配）、扣账取**预扣—结算**，其余裁决口径见 `docs/superpowers/specs/2026-10-05-eng-005-budget-accounting.md`。Router 的成本输入由此定为**预算视图**（见 §4.1 与 §4.3）。

**OPEN-007 阻断节点放置。** Artifact 隐私等级的赋值规则与传播规则未定义，放置判定缺少输入。

**OPEN-008 影响评分体系。** Population Feedback 的数据来源未定义，冷启动期 Router 退化为仅使用画像与个人反馈。

# 5. 边界层工程

对应《总纲》第 5 章。本层定义不可逾越的约束及其强制执行点。§342 十条不变量中，第 2、3、7、8 条由本层承担。

## 5.1 建设内容

| 组件 | 规范依据 |
|---|---|
| Workspace 抽象与只读强制 | §254 §256 |
| Task Workspace（worktree / overlay） | §255 |
| Integration Gate | §257 |
| Capability 强制执行点 | §253 |
| Effect Journal | §267 §268 §269 |
| Audit Log | §313 |
| Policy Engine 与优先级 | §104 §105 |
| 密钥运行时 | §51 §100 §103 |
| Prompt 信任标签强制 | §281 §50 |
| Authority Host | §292 §293 |
| Standby 与故障转移 | §294 §295 §296 §297 §298 |
| Connector 与权限细分（中立） | §124 §125 |

## 5.2 组件边界

**Workspace 强制** 是本层的主要强制点。§256 要求 `AI_WRITE(BaseWorkspace) = DENY`，§159 要求这是文件系统级保证而非 prompt 约定。

Rust 的实现方式是把可写路径编码为独立类型，写操作只接受该类型。Base Workspace 的路径无法构造出可写类型，因此写操作在类型层面不可表达。这是本层相对其他语言的主要收益。

**Task Workspace** 对 Git 项目使用 worktree（§255），非 Git 项目使用 overlay 类机制。两条路径共享同一个 Workspace 抽象，上层不感知差异。

**Integration Gate** 是 Task Workspace 到 Base Workspace 的唯一通道（§257），支持 view diff / apply patch / cherry-pick / merge / discard 五种操作。

**Effect Journal** 覆盖所有不可通过 Artifact 回滚的外部操作（§268）。写入顺序是执行前记录（§268），而非执行后补记。`idempotency_key` 用于防止重试产生重复副作用。

**Policy Engine** 实现六级优先级（§105）。该优先级表是硬性的，不参与学习（§321）。

**Prompt 信任标签** 的强制点在本层而非第 6 层：标签由 Context Compiler 附加，但拒绝行为必须由本层保证（§281 要求外部内容不得与用户指令处于同一信任级别）。

**Authority Host** 仅在其成为 Product Drive 对象时进入本层建设范围。个人网络相关组件属于长期范围（§58 第三阶段）。

## 5.3 层内依赖

```
Workspace 抽象 ← 无
Task Workspace ← Workspace 抽象
Integration Gate ← Task Workspace + Base Workspace
Capability 执行点 ← 第 4 层 Capability Token
Effect Journal ← Capability 执行点
Audit Log ← 独立
Policy Engine ← 独立
密钥运行时 ← Capability 执行点
Connector ← 密钥运行时 + 第 4 层 Capability Token     补于 2026-10-05：本组件由 §4.1 移入本层（裁决见 docs/superpowers/specs/2026-10-05-p3-bcdf-set-decisions.md）
Prompt 信任标签强制 ← 第 6 层 Context Compiler
Authority Host ← 独立（长期）
Standby ← Authority Host（长期）
```

## 5.4 完成判据

```
对 Base Workspace 的写请求被拒绝，且拒绝发生在类型层或文件系统层，可独立验证
Task Workspace 的修改只能经 Integration Gate 进入 Base Workspace
所有不可回滚外部操作在执行前写入 Effect Journal
Runtime 重启后能根据 Journal 恢复未完成的 Effect 状态
Policy 冲突按 §105 六级优先级裁决
```

## 5.5 相关缺口

**OPEN-013 直接作用于本层的可学习边界。** §320 允许学习 routing policy、planning heuristics、execution method、verification strategy、context selection；§321 禁止自动修改 Authority、Contract、Permission、approval、security 语义。执行该分界线的机制自身属于哪一类未定义。若该机制可被学习，则本层的强制可以被学习过程取消。

**A14 影响 Resource Arbiter 的暴露面**（§300）。该组件位于第 7 层，但其隐私保证的强制点在本层。

**B4 影响 Audit Log。** §313 列出了必须记录的事件类型，未定义保留期与防篡改机制。

**B5 影响 Temporary Authority 的限制强度。** §296 使用 SHOULD，与 §342 第 7、8 条不变量的强度不匹配。

# 6. 认知层工程

对应《总纲》第 6 章。本层确定模型在每一步看到什么，以及系统跨时间记住什么。它同时是隐私边界与成本边界的执行点。

## 6.1 建设内容

| 组件 | 规范依据 |
|---|---|
| Memory Source Graph | §282 §170 |
| MemoryClaim 存储 | §283 §284 §179 |
| Memory Synthesis 后台作业 | §285 §171 §172 |
| Memory Correction | §286 §177 |
| Context Compiler | §279 §280 §70 |
| Context Provenance 与信任标签 | §281 §71 |
| Runtime Learning | §320 §216 |
| Protected Core | §321 §322 |

## 6.2 组件边界

**Memory Source Graph** 是事实来源，MemoryClaim 是派生表示（§282）。两者的关系是：删除 Source 必须使派生 claim 失效；删除 claim 不影响 Source。

**Memory Synthesis** 是后台作业（§285），输入为 Source 集合，输出为 claim 集合与 Memory Summary。它是 §169 所述 Dreaming 机制的实现，不以条目表为核心。

**Memory Correction** 产生新的 Correction Source，使旧 claim 进入 SUPERSEDED（§286），不覆盖历史。

**Context Compiler** 是节点执行的强制通道（§279 MUST），同时实现四个目标：减少 token、降低隐私暴露、减少无关信息、降低 prompt injection 面（§70）。

**Context Provenance** 附加信任标签（§281）。标签的附加在本层，拒绝行为在第 5 层。

**Protected Core** 是本层唯一必须先于其他组件存在的部分。Runtime Learning 需要一条不可被自身修改的边界（§321），该边界必须先于学习机制存在，否则学习没有依据。

## 6.3 层内依赖

```
Memory Source Graph ← 无
MemoryClaim ← Memory Source Graph
Memory Synthesis ← MemoryClaim + Source 集合
Memory Correction ← MemoryClaim + Source 集合
Context Compiler ← MemoryClaim + Artifact + Conversation
Context Provenance ← Context Compiler
Protected Core ← 无
Runtime Learning ← 执行历史（第 3、4 层）+ Protected Core
```

Protected Core 与 Runtime Learning 之间存在单向依赖：Learning 读 Protected Core，不能写。

## 6.4 完成判据

```
节点执行前必经 Context Compiler，不存在绕过路径
Context Package 中每段数据带来源标签，外部内容与用户指令标签不同
用户纠正生成新的 Correction Source，旧 claim 进入 SUPERSEDED
Runtime Learning 的产物无法修改 §321 列出的五类语义
```

## 6.5 相关缺口

**OPEN-013 阻断本层建设。** §320 与 §321 划定了可学习与不可学习的范围，但执行该分界线的机制自身归属未定义。实现上必须先确定 Protected Core 的强制形态，否则本层无法落地。

**C4 / OPEN-016 影响 Context Compiler 的定位。** §279 要求节点执行前必须通过 Context Compiler，§69 指出 Context 也属于 capability。capability 判定发生在 Compiler 内部还是外部，决定 Compiler 是否必须纳入 Protected Core。

# 7. 长期循环工程

对应《总纲》第 7 章。本层处理系统在没有明确终点时如何持续推进。

## 7.1 建设内容

| 组件 | 规范依据 |
|---|---|
| Product 对象与 ProductReadiness | §231 §232 §153 |
| Milestone 生成 | §233 §234 §151 §152 |
| Progress Gate | §337 §154 |
| Shippable Predicate | §335 §336 §155 |
| Background Supervisor | §299 §12 |
| Resource Arbiter | §300 §13 §14 |
| Session Orchestrator | §11 |
| 三层调度 | §301 §302 §303 §304 §77 |

## 7.2 组件边界

**三层调度必须相互分离**（§301）。Intent Scheduler 包含模型判断（§302 的输入含 user focus、background suitability），Graph Scheduler 是确定性逻辑（§303），Resource Scheduler 落在第 4 层。

**Milestone 生成** 采用有限视野（§233），禁止一次生成完整未来。Milestone 之间的关系不限于线性，允许并行与汇合（§152）。

**Progress Gate** 检测 `progress_delta`（§337）。连续多个 Milestone 无实际进展时强制 replan。

**Resource Arbiter 独立于 AI 模型运行**（§13）。这是该组件的定义性特征：它必须在模型不可用时仍能工作，因此不能依赖第 4 层的任何组件。

**Background Supervisor** 的任务来源限于四类（§299）。

## 7.3 层内依赖

```
Product ← 第 2 层 Intent
ProductReadiness ← Product + 第 8 层验证结果
Milestone 生成 ← Product + ProductReadiness
Progress Gate ← Milestone 历史 + ProductReadiness
Resource Arbiter ← 无（独立于模型层）
Background Supervisor ← Resource Arbiter + Intent Scheduler
Session Orchestrator ← Intent 存储 + Background Supervisor
Shippable 判定 ← ProductReadiness + 第 8 层 Completion Predicate
```

Resource Arbiter 的入度为零。它是本层唯一不依赖其他层的组件，也是本层唯一必须在 AI 不可用时仍然可用的组件。

## 7.4 完成判据

```
Milestone 逐个生成，系统中不存在预先定义的完整 Milestone 列表
Progress Gate 在连续无进展时触发 replan 并生成 Decision
Resource Arbiter 在模型层完全不可用的情况下仍能限制后台负载
Shippable 与 post-shippable 两种状态被区分，不互相覆盖
```

## 7.5 相关缺口

**A15 / OPEN-010 影响 Progress Gate。** §232 用九个维度描述 ProductReadiness，§337 要求 `progress_delta` 接近零时触发重新规划，但九个维度的聚合函数与阈值未定义。该组件当前无法判定为触发或未触发。

**OPEN-015 影响 Milestone 生成。** §233 要求有限视野，§152 允许并行与汇合，二者的组合会使下一批覆盖多个未来状态，批次边界未定义。
