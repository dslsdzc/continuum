# DSH 对照分析

本文对照 DeepSeek Harness（下称 DSH）与《总纲》《工程文档》所定义的 Continuum / PIER，判定哪些实现可作参考、哪些不可搬。

## 0. 事实来源与不确定度

DSH 版本 `0.2.0-rc.2`，MIT，仓库 `github.com/deepseek-ai/deepseek-harness`，本地副本 `/tmp/dsh-src`（`git clone --depth 1`）。

本文的结构性结论来自一次自动化源码扫读（包清单、接口定义、循环流程、持久化路径）。**未逐行阅读 DSH 源码**，未运行其测试，未验证其运行时行为。凡引用具体符号名与路径的，均来自该扫读记录；凡属判断的，在文中标明为判断。

## 1. 规模基线

```
工作区包        507 个（packages/ 下 316 个，全部命名 @deepseek-ai/dsh-*）
TypeScript      约 41.5 万行（不含 node_modules）
测试文件        1627 个 *.spec.ts / *.test.ts，270 个 *.e2e.ts
源码体积        185 MB
Rust 代码       0 行，无 Cargo.toml
原生代码        C，仅限 native/system
```

与 Continuum 的对比基线：§343 定义的 v0.1 范围 16 项；02 §10.1 列出的阻断项 5 项。

DSH 的形态包含 Electron 桌面端、浏览器端、Python SDK、单可执行文件分发、Landlock 沙箱启动器、PTY 后端、Office 引擎接入、computer-use 与 browser-use。这些均不在 §343 的 v0.1 范围内。

## 2. 与 02 七层的逐层映射

对应强度分三档：**强**（机制同构，接口可对照）、**弱**（问题相同、解法不同）、**无**（无对应物）。

| 层 | DSH 对应物 | 强度 | 说明 |
|---|---|---|---|
| 2 语义层 | 无 | 无 | DSH 无 Contract、Specification、ContractDiff、Constraint Validator、Budget、Decision 对象。有 `plan`（1 包）、`goal`（4 包）、`todo`，均为任务清单性质，非版本化约束 |
| 3 执行层 | `packages/core/agent-loop` | 弱 | 2490 行，`kick()` / `turn()` / `step()` 三段式，`tool-calls.ts` 做并行调度。**这是会话式 react 循环，不是 §235 的类型化数据流图**。§239 Port 类型系统、§306 图失效传播、§305 增量重算在 DSH 中无对应物 |
| 4 资源层 | `packages/llm/llm`、`packages/core/tools` | 强 | 见 2.1 |
| 5 边界层 | `native/system`、`packages/sandbox/*`、`packages/interaction/user-approval`、`packages/session/session-persistence-jsonl` | 强 | 见 2.2 |
| 6 认知层 | `packages/context/*`、`packages/compaction/*`、systemPrompt.assemble | 弱 | 有上下文装配与压缩，无 §282 Memory Source Graph、§283 MemoryClaim、§285 Memory Synthesis、§320 Runtime Learning、§322 Protected Core |
| 7 长期循环 | 无 | 无 | 无 Product 对象、无 §233 Milestone 生成、无 §337 Progress Gate、无 §335 Shippable |
| 8 跨领域 | `packages/skill`（6 包） | 无 | 无 §258 Evidence 数据模型、无 §260 Requirement Coverage、无 §262 Verifier 优先级、无 §266 Completion Predicate |

### 2.1 资源层的对应（强）

```
Continuum §315 ModelProvider     DSH LlmAdapter（packages/llm/llm/src/index.ts:208）
  list_models                      listModels(provider)
  describe_model                   resolveModel(provider, model, signal)
  invoke / stream                  stream(options): AsyncIterable<StreamChunk>（唯一必需方法）
  cancel                           —（经 AbortSignal，非独立方法）
  usage                            —（usage 在 assistant/message 事件里）
  health                           providerInfo(provider)
```

方法集不同，但边界角色一致。DSH 另有 `prepareCall` / `PreparedLlmCall` 与 `AdapterRegistrationHandle.replace()`，前者把「冻结请求」与「发起请求」分离，后者允许整组 provider 替换。

```
Continuum §316 ToolProvider + §244 Operator 注册表
                                 DSH ToolRuntime（packages/core/tools/src/index.ts:807）
  §252 Capability / §105 Policy   DSH ApprovalService（packages/interaction/user-approval）
  §256 只读工作区默认             DSH SandboxPolicy 默认 read-only
```

DSH 的 `ToolDefinition` 字段（`name`、`description`、`parameters`、`output`、`execute`、`timeoutMs`、`isConcurrencySafe`、`presentCall`、`presentResult`）比 02 §3.1 的组件清单更具体，可作为 §244 的取值参考。

审批粒度是**每次工具调用一次**（`ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'`），且无审批服务时 `ask` 降级为 deny。这与 §124 / §125 要求的「按操作细分、不得退化为服务级授权」同向。

沙箱模式 `read-only | workspace-write | danger-full-access`，默认 `read-only`，与 §256 的 `AI_WRITE(BaseWorkspace) = DENY` 同向。

### 2.2 边界层的对应（强）

`native/system` 是 C 写的两部分：

```
landlock-run    native/system/packages/entry/src/main.c   独立静态可执行文件（musl-gcc，-static -s）
system.node     native/system/packages/entry/src/flock.c  N-API addon，POSIX 独占 flock
```

这直接对应 §159 的要求：只读工作区必须是**文件系统级保证而非 prompt 约定**。DSH 用 Landlock 做到这一点，并预编译 linux/darwin × x64/arm64 五套包。

`packages/session/session-persistence-jsonl` 是耐久写入实现：

```
每 session 一个 append-only JSONL 文件
压缩：zstd（默认，带校验和帧）或 none（纯文本）
tornTruncateTo    首个新 append 前截断撕裂的物理尾
recoveredTail     从撕裂帧恢复事件，首次变更时重写为持久化
lease.ts          跨进程写锁；内核在持有者死亡时自动释放，故意不设过期
                  加锁对象是 inode 而非路径，加锁后校验 inode 未被替换
```

## 3. 与规范核心不变量的对照

《总纲》结语列出三项核心不变量。逐条对照：

| 不变量 | DSH 对应物 | 结论 |
|---|---|---|
| Contract 不可越权（§225）：Runtime 可改 HOW，不可改 WHAT | 无。DSH 无 Contract 对象，无 WHAT / HOW 分离 | 无对应 |
| Base Workspace 不可写（§256） | SandboxPolicy 默认 read-only + Landlock 文件系统级强制 | **同向，且有可参考的实现** |
| 完成不由模型宣告（§266）：由 Completion Predicate 与 Evidence 裁定 | 无。DSH 的 turn 结束由模型不再产生 tool-call 决定 | 无对应，且方向相反 |

第二项有实现可参考，第一、三项无对应物。这不是 DSH 的缺陷——§225 与 §266 是 Continuum 独有的设计取舍，DSH 不在同一问题域。

## 4. 与 P0 直接相关的三项发现

**4.1 持久化形态与 02 §1.4 冲突。** 02 §1.4 把持久化绑定为 SQLite，理由是 §318 要求事务语义。DSH 的选择相反：会话日志用 append-only JSONL + 写锁 + 撕裂尾修复，非会话 KV 才用 SQLite。`packages/storage/storage-sqlite/src/unit.ts` 明确写到依赖 SQLite 单语句原子性，**不设显式事务、不设写队列**。

即：DSH 不以事务边界解决跨实体一致性，而以「单一 append 批 + 锁」解决。若采用 DSH 的形态，P0 设计第 4 节（事务 API）与 02 §1.4 都需修订。

**4.2 DSH 有格式迁移链的成熟做法。** 会话格式按相邻版本迁移（v0→v1→v2→v3→v4，每版一个包，构造时校验 gap-free），已提交世代不可移动、不可覆盖、不可删除；`SessionEventMap` 的成员默认读时必需，不认识该事件类型的构建会拒绝整份日志，除非事件带 `ignorable: true`。

这与 P0 设计第 5 节的 Event Stream 版本策略同向，且比 02 现有描述更具体。P0 的 `schema_version` 取值可直接参照这套规则。

**4.3 崩溃恢复的做法。** `session-format` 的 `createRestore(header, {recovery})` 返回可恢复解码器，允许丢弃一个畸形行及其未提交后缀；但若该行之后出现 `turn/end`，原始问题升级为致命。`packages/session/session/src/repair.ts`（211 行）另有日志修复逻辑。

§319 只给了五个阶段的名称，未定义各阶段的判定规则。DSH 这套「可恢复前缀 + 升级为致命」的判定可作为 §319 的实现参考。

## 5. 结论

**DSH 不实现 Continuum。** 它覆盖 02 七层中的第 4、5 层，第 3、6 层只有弱对应，第 2、7、8 层无对应物。Continuum 的规范核心——Contract、Plan 审查阶梯、Requirement Coverage、Completion Predicate、Product Drive——在 DSH 中均不存在。

可搬的是机制：Landlock 沙箱强制、会话日志的耐久写入与撕裂尾修复、格式迁移链、审批的 per-call 粒度、工具定义的具体字段。

不可搬的是规范：§225、§266、§342 十条不变量所表达的约束在 DSH 中无载体，且 §342 第 9 条（Runtime 不能自行取消边界规则）与 cordis 的可替换内核（一切注册都是可回滚的 `ctx.effect()`）方向相反。

因此「以 DSH 源码为基底重写为 Rust」在语义上不成立：可搬的部分（机制）与要建的部分（规范）不重叠。可行的形态是**在机制层参考 DSH，在规范层继续从零实现**。

未决：本文未评估 DSH 的测试基础设施（1627 个单测 + 270 个 e2e + 覆盖率门 100%/文件）与 benchmarks 组织方式是否值得借鉴。
